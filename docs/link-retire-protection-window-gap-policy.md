# 淘汰链接审核：保护窗口缺日策略（2026-09-18 决定）

## 结论

窗口内缺一天观测时，**保持 `cannotJudge`（fail closed），不做顺延桥接**；缺口日按算术自然退出窗口后，受影响的行自行收敛。这是**已确认的策略，不是待修缺陷**。

## 为什么缺日不能桥接

保护线判定的核心是「15 天内是否发生过恢复/重新在售」。若把相邻日（如 09-04）的观测顺延到缺口日（09-05），一条 `09-04 有货 → 09-05 售罄 → 09-06 补货` 的链接会被读成「一直有货」，从而**被误判为候选、绕过保护线**。桥接等于用推断替换观测，风险不可接受。

实测（2026-09-18，仅把 09-04 顺延到 09-05 的对照实验）：129 条待确认里 128 条立即变候选、1 条（DL `SK-446电动刀与切片器` / `sv260203191924749603938`，09-04=0、09-06=58）被正确识别为 15 天内恢复而排除。也就是说 129 条**全部只卡在这一天**——正因为影响面这么大，才更不能靠顺延解决。

## 窗口算术

- 窗口 = `[runDate - 15, runDate]`，共 **16** 天（含审核日）；恢复判定 cutoff = `runDate - 14`。
- 缺口日 `G` 离开窗口的条件：`runDate - 15 > G`，即 `runDate > G + 15`。
- **2026-09-05 的缺口自 runDate 2026-09-21 起退出窗口**；09-19、09-20 仍在窗口内，09-21 起 09-04 与 09-05 同时出窗。

契约测试：`scripts/test_link_retire_missing_day_window.mjs`（已注册进 deterministic shards）钉住窗口 16 天、缺日在窗内必须 fail closed、缺日退出日期为 2026-09-21、无缺口的同一行必须是候选（证明 cannotJudge 只由缺日造成）、以及**复制相邻日观测不被接受**。

## 缺日的成因与可恢复性

2026-09-05 的观测在**任何来源都不存在**：

| 来源 | 覆盖 |
|---|---|
| 老云 `outputs/shein_links/<store>/` | 08-13…09-04 与 09-06…09-14，**恰好跳过 09-05** |
| 新宿主 `outputs/shein_links/<store>/` | 同（迁移自老云） |
| `fact.visible_inventory_snapshot` | 新旧两端都缺 09-05 |
| 老云 morning 链 | 2026-09-06 的 `morning-all` marker 为 **failed**（businessDate 09-05，deadline expired）→ 当天链路未产出工件 |

所以这不是迁移丢失，也无法补抓（SHEIN 不回放历史）。

## 与保留策略的关系

逐日原始工件是这条窗口的**唯一**可证来源：`fact.link_master_snapshot` 在新旧两端都只有单日数据，数据库那条通道撑不起 16 天窗口。因此产出保留期必须 ≥ 16 天（当前 `cloud_disk_maintenance.sh` 默认 30 天，见 `test_link_retire_history_retention.mjs`），否则窗口会因保留不足而出现**人为缺日**。

## 若将来要立刻收敛

需要新增一条**显式**缺口容忍契约（例如「缺口日两侧都有观测且同号时按无恢复处理」），并同时落地：规则文档、契约测试、以及该容忍在报告里的独立标注（不能让读者以为窗口是完整的）。当前未采纳。
