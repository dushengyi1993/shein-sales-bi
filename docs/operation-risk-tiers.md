# 业务操作与测试的风险分级

这四层规则用来决定今天该做什么验证。业务动作的风险，不能因为它听起来重要，就自动升级成全仓代码测试。

## 第一层：纯只读业务

例如查销售、查库存、查订单状态、核对活动或确认某个链接当前状态。直接执行确定性的 `query`，读取云端或其他 live evidence，并根据返回的结构化数据下结论。

这一层不做 hash，也不跑仓库测试。查询失败、数据不完整或证据过期时，报告失败或不完整，不把它改写成 0 或“已完成”。

## 第二层：无代码变更的受控业务写

例如已经授权的上链接、库存纠正、活动或价格调整。固定顺序：

`fresh preflight → 一次 exact payload/plan hash → 串行 execute → live readback`

- 用户清晰的业务命令（如明确商品、店铺、价格、库存或决策指令）即为执行授权。严禁在执行前反复向用户要求确认同一事项，禁止让用户手动搬运 hash。
- `waiting_review` 是系统进入可执行就绪的技术状态，可由当前任务直接衔接执行，不等同于必须再次向用户提问。
- 内部 `--confirm` 确认词继续由 agent 自动传递，无需用户介入输入。
- 已获用户授权的低利润等特殊业务设定为单项有效，不得在后续步骤中重复拦截或要求重新确认。
- 只有发生真实代码缺陷或需发布时才归入 V6 修复开发，其余业务任务均由各自业务工作流独立执行，无需向 V6 申请或审批业务权限。
- 这层不跑 `npm test`，也不发版。只有在 preflight 发现未授权对象、payload 校验不通过或最终回读发生漂移时，才停止并报警；不能用仓库测试结果代替业务写入的 live readback。

## 第三层：局部代码修复

代码有局部改动时，先做语法检查和 diff 检查，再跑精确相关测试。可以使用 `test:focused`，例如：

```text
npm run test:focused -- scripts/test_product_display_name.mjs,scripts/test_product_sku_normalizer.mjs
```

这个入口只接受 deterministic runner 注册表中的精确路径；重复路径会去重，未知路径、空值、路径穿越以及和 `--shard` 同时使用都会失败。它不会触发 `build:portal-shell` 或 `check:source`，也不会暗中扩大为全仓测试。

## 第四层：跨模块集成或正式发布

只有跨模块集成、发布前完整回归或正式发布，才运行完整本地 suite。CI 是发布审计和门禁证据，不应为了今天的业务操作阻断当日工作。

如果当前 GitHub 额度故障，禁止从 `origin/main` 假定生产基线；应以已核实的发布提交、部署状态和 live readback 为准，并明确标记无法确认的部分。

## 明确反对的升级

“待议价”“上链接”“库存纠正”等业务操作，不因为名称或影响范围就升级为全仓测试。没有代码变更时按第二层的受控写流程办；有局部代码变更时按第三层只验证相关代码。只有确实发生跨模块集成或正式发布，才进入第四层。
