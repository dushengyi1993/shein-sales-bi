# SHEIN 营销活动报名价格规则

## 适用范围

- 适用于 SHEIN 商家后台“营销活动报名”里的活动填报。
- 也适用于报名前的优惠券、限时折扣和既有营销活动叠加风险审核；用户明确要求开始报新活动前，本规则只用于只读审核和生成复核文档。
- 普通营销活动是平台给流量扶持的主活动层：只要商品符合本期策略且仍在报名窗口内，原则上必须报名；报名窗口和活动生效窗口分开判断，不能等生效日才想起来补报。
- 自动化只负责：
  - 勾选商品
  - 填写 `提报的活动价格`
  - 填写 `提报的活动降幅`
  - 滚动复核
- 自动化默认 **不得点击** 最终 `提交报名`；只有用户在本轮明确授权“你自己提交/全自动报完”时才可真实提交，并且提交后必须用后台已报集合回读验证。
- 页面里 `提报的活动价格（实际生效参考此列）` 优先级最高；`提报的活动降幅` 主要用于配合平台校验。
- 若普通营销活动、优惠券和限时折扣存在时间重叠，报名前必须先做“保底成交价 + 触券下探风险”审核，不能只看本次活动价。

## 价格叠加安全红线

已验证风险样本：`2026-06-01` HL 店 `SK-04031胶囊咖啡机` 订单净收入 `183.89 SAR`，商品成本 `182.52 SAR`，不含仓储费利润率仅 `0.74%`；同货号 HL 在 `2026-05-31` 的活动标签同时包含 `SA-超级爆品活动-第42期`、`#HLSDdsy1993#限时折扣#2026-05-03#1` 和 `2026年「度假季」常规活动-全托 半托（本地）`。根因模型是：同一时间多个促销价重叠时，SHEIN 取最低促销价；若商品还报名优惠券，则优惠券继续作用在该最低价上。

因此后续所有活动报名必须按以下保守模型审核：

1. 对每个 `店铺 + SKC + 时间窗口`，先列出所有可能生效的价格来源：
   - 当前原始价 / 划线价 / 当前售价
   - 已报名、已生效、未来将生效的普通营销活动价
   - 本地已知普通活动填报价证据（例如 `tmp/mbrs/deadline-fill-results/*.json` 中仍在生效窗口内的填报价）
   - 已设置、已生效、未来将生效的限时折扣价
   - 已报名或计划报名的优惠券活动、券档、预算和生效范围
2. 对每个时间窗口计算最低促销基准价：

   `最低促销基准价 = min(当前售价, 普通营销活动价..., 限时折扣价...)`

   同一 `SKC` 若存在多条已生效或未来生效的限时折扣，必须按该时间窗口内 **最低** 的 `limitedDiscountPrice` 判定风险，不能取第一条、最新一条或活动列表顺序。

3. `2026-06-14` 起优惠券不是每单必然触发，不能再作为保底成交价层。必须拆成两套价格：

   `保底成交价 = 最低促销基准价`

   `触券下探价 = 最低促销基准价 × (1 - 商家承担优惠券折扣率)`

   保底成交价用于判断买家不触券时是否仍达到本期 `finalTargetPrice`；触券下探价只用于判断“如果券触发，会不会低于底价/利润红线”。若优惠券状态、券档或预算不确定，只能按风险线索处理，不能用“假定有券”证明价格达标。

   **禁止仅凭活动标签做真实取消或报名。** `度假季`、旧普通活动、旧限时折扣、优惠券标签都只能生成风险候选；真实动作必须继续比较保底成交价、触券下探价与本期目标/底线：

   - 若 `保底成交价 < finalTargetPrice`（超过平台取整/`1 SAR` 容差），说明活动层本身低于目标价，应取消或调高最低且可控的活动层，必要时临时下架止损。
   - 若 `保底成交价 ≈ finalTargetPrice`，说明普通活动价或限时折扣价本身能保障目标成交价。
   - 若 `保底成交价 > finalTargetPrice`，说明价格偏高；应补齐普通营销活动或用限时折扣兜底到目标价，不能靠优惠券“算下来”。
   - 若 `触券下探价` 低于底价/利润线，即使保底价达标，也不得把该 SKC 放进 15% 券，除非用户单独确认清货亏本试验。
   - 历史“普通活动 + 仅15%券”计划必须迁移：取消作为价格保障的优惠券，改由普通活动价或限时折扣价直接命中目标。
   - 若旧普通活动填报价证据显示旧普通活动价本身低于目标，或触券下探价会打穿底线，必须先阻断优惠券提交/日报 no-action；这类证据即使来自旧填价文件而非当前提交器，也不能忽略。
   - 若商品存在旧普通活动标签但缺旧普通活动价证据，不能当作安全，也不能把“缺证据”丢给用户；系统必须自动触发只读取证（live 扫描 / 后台回读普通活动已报商品价）。只有登录失效、店铺身份不确定、平台接口不可达等系统取不到证据的情况，才报告具体阻塞。
   - 若脚本使用 `--allow-limited-discount-overlap` 这类人工覆盖参数，必须有逐 `SKC` 的价格证据；该参数只能临时用于已审核补救，不得作为默认自动化策略。
4. 利润率必须同时展示两套：

   `商品利润率 = (保底成交价 - 商品完整成本) / 保底成交价`

   `含仓储费利润率 = (保底成交价 - 商品完整成本 - 仓储费摊销/件) / 保底成交价`

   若本行允许 15% 流量券，审核表还要额外展示“触券下探利润率”，用于判断引流是否会打穿底线。

5. 安全判断默认以 `含仓储费利润率` 为主；若仓储费缺失，审核表必须标记 `仓储费缺失/估算缺失`，不得把仓储费按 0 当成已安全。
6. 普通商品默认目标仍按 `30%` 左右利润率；新品/正常品报名前的含仓储费利润率原则上不得低于 `20%`。库存沉淀清货可以按 `15%` 含仓储费利润率作为低价底线，但必须在审核表标红并由用户逐项确认；低于 `15%` 的最终成交价禁止自动报名，除非用户在备注栏单独点名确认。
7. 固定价规则里的固定价从此按“目标最终成交价”理解，不再默认等于“普通活动价”。如果还叠加 `15%` 优惠券，应反推普通活动价；如果已有更低旧活动或限时折扣，则固定价目标视为失效并进入高风险复核。
8. 同一标准货号在所有店铺、所有链接中按 BI 曝光量取全局前五链接；这五个链接可以比其他链接低 `5` 个百分点目标利润率，但不得低于 `15%` 底价。如果基础目标利润率本来就是 `15%`，前五链接保持 `15%`，其他链接提高到 `20%`，避免把底线继续向下打穿。不能按单店拆出多个“前五”。
9. 固定价和逐行覆盖价优先于曝光前五规则；曝光前五只调整利润率型自动定价，不能覆盖用户在本期审核表里确认的具体价格。

## 报名前审核文档要求

每次报活动前必须先生成给用户复核的审核文档；用户确认前不得报名新活动、不得批量取消或重报限时折扣。审核文档至少包含以下字段：

| 字段组 | 必填字段 |
| --- | --- |
| 商品定位 | 店铺、分组、活动 ID/名称、SKC、SKU、供方货号、标准货号、商品标题/中文名 |
| 时间窗口 | 报名截止、普通活动开始/结束、优惠券开始/结束或活动期、限时折扣开始/结束、是否与既有活动重叠 |
| 原始价格 | 原价/划线价、当前售价、SHEIN 页面/API 价格字段来源、平台最低降幅 |
| 成本 | 商品完整成本、仓储费摊销/件、含仓储费成本、仓储费口径、成本缺失/仓储费缺失标记 |
| 本次建议 | 建议普通活动价、建议普通活动折扣、建议限时折扣价/折扣、是否使用可选 15% 流量券 |
| 价格测算 | 最低促销基准价、保底成交价、触券下探价、商品利润率、含仓储费利润率、最低价来源 |
| 风险提示 | 旧活动重叠、限时折扣更低、优惠券可叠加、平台最低折扣压价、预算异常、利润率低于红线、缺成本/缺仓储费 |
| 用户复核 | 修改意见/备注、用户确认动作、是否允许低于默认红线、是否需要取消旧限时折扣 |

审核文档应同时提供“明细行”与“按标准货号汇总”两种视图：明细行用于逐 SKC 防漏，汇总视图用于用户快速看价格区间和风险。用户在 `修改意见/备注` 中确认后，才能转换成本期覆盖文件；覆盖文件必须保留用户备注来源。

### 用户确认方案的固定输出格式

给用户看的方案必须是 Excel 工作簿（`.xlsx`）为主，Markdown 只做摘要入口，JSON/CSV 只给脚本和复核使用。不能只给用户一张几百行明细表，也不能只给 CSV/JSON。

工作簿至少包含：

| Sheet | 作用 | 必填内容 |
| --- | --- | --- |
| `说明` | 告诉用户本方案能不能直接报、哪些动作未执行 | 数据日期、活动范围、候选数、可报数、剔除数、是否真实提交、后续执行边界 |
| `按货号汇总` | 用户主审入口，一行看懂一个标准货号 | 标准货号、商品名、活动 ID 分布、覆盖店铺数/SKC 数、预期利润率、预期最终价区间、普通活动填报价区间、是否使用可选 15% 流量券、触券下探价区间、曝光前五口径、缺 7 天曝光原因、剔除/阻塞摘要、备注 |
| `店铺差异明细` | 解释同一货号不同店为何价格不同 | 店铺、SKC、活动 ID、当前售价、平台最低降幅、目标利润率、曝光排名/是否前五、普通活动价、最终成交价、仓储费、利润率、差异原因、备注 |
| `报名明细` | 执行 allowlist，防漏报/错报 | 店铺、活动 ID/名称、SKC、标准货号、提报活动价、提报折扣、`finalTargetPrice`、`couponFactor/combo`、价格来源、是否提交、备注 |
| `剔除项/阻塞项` | 说明为什么不报 | 店铺、SKC、标准货号、剔除原因、缺成本/缺仓储/平台状态/库存/货号待归并/低于底价/缺覆盖价等证据、下一步、备注 |
| `低价补救/风险项` | 把当前风险和本次报名分开 | 店铺、SKC、标准货号、订单成交价或最低基准价、目标价、差额、风险来源、已处理/待观察/需授权动作、备注 |
| `15%券流量试验计划` | 可选流量券方案，不承担价格保障 | 店铺、SKC、标准货号、普通活动填报价/限时折扣保底价、券活动 ID、`couponFactor=0.85`、保底成交价、触券下探价、使用理由（高曝光/滞销/清货）、预算建议、禁止 30%/50% 券、执行前检查、备注 |

格式硬要求：

- 除 `说明` 页外，每个 sheet 都必须有 `备注` 或 `修改意见` 列，供用户直接标注。
- `按货号汇总` 必须体现用户关心的业务判断：预期利润率、预期价格、曝光前五影响、是否配优惠券、剔除项原因；不能只列店铺/SKC/活动价。
- 同一标准货号在不同店铺方案有差异时，必须能在 `店铺差异明细` 里看到差异来源（曝光前五、平台最低降幅、当前售价、成本/仓储、固定价/指定利润率、覆盖价）。
- `15%券流量试验计划` 必须和价格保障动作分开表达：普通活动/限时折扣先保证保底成交价；只有高曝光支持、全店高库存滞销品引流或清货试验才准备可选券。上券前必须刷新预算、旧普通活动、限时折扣和已报集合证据。
- `剔除项/阻塞项` 不是“丢弃清单”，而是后续补证据/补成本/等库存/等平台状态恢复的动作来源。
- 给用户的摘要必须按货号说人话：例如“此货号可报多少店、目标利润率是多少、前五链接怎么处理、是否配 15% 券、哪些店不同、为什么剔除”。不要把 800 行明细直接丢给用户当主方案。

## 货号归并前置规则

- 报价前必须先做货号归并，统一使用：
  - `config/product_catalog.json`
  - `config/product_aliases.json`
  - `lib/product_sku_normalizer.mjs`
- 仓库侧 `dim.product_match_key()` / `dim.product_canonical_sn()` 必须由 `scripts/generate_product_match_key_schema.mjs` 从 `config/product_aliases.json` 生成并应用，不能手写另一份别名逻辑；否则 ET 仓储明细会按短码散落，确认表会出现缺仓储或旧别名独立行。
- 只有短码、纯数字或 normalizer 标为 `needsReview` 的货号，必须在确认表里标为“货号待归并，暂停”，不得作为可报名 SKU 自动出价。
- 典型归并：
  - `TXSM-505A电动缝纫机` / `SM-505A电动缝纫机` -> 同款
  - `SK-7025绞肉机` / `SK-7025A绞肉机` -> 同款
  - `便携式咖啡机` / `KF-JN-02便携咖啡机` -> 同款
  - `185` -> `SK-185台式榨汁机`
  - `03012` -> `SK-03012台式榨汁机`
  - `03038` / `制冰机` -> `SK-03038制冰机`
  - `SK-3065` -> `SK-GT-3065蒸汽熨烫机`
  - `SK-675` -> `SK-JFB-675B卷发钳和卷发棒`
  - `SK-13065布衣清洗机` -> `SK-13065吸尘器`

## 报价优先级

1. 本期用户确认表 / 备注生成的逐店铺 + 活动 + SKC 覆盖价（row-level override）
2. 用户指定固定价
3. 用户指定利润率
4. 新品保护价
5. 库存沉淀 / 清货候选价
6. 默认利润率规则
7. 平台活动强制档位 / `VIP档` 最低降幅 / 页面回写结果复核（作为最终硬约束记录）

平台最低降幅不是固定 `10%`：大多数活动可能要求 `10%`，少数活动可能要求 `5%`，也可能存在 `VIP档`。执行时必须读取活动页/API 的实际最低降幅或 VIP 档位；若 `VIP档` 强制导致价格低于本期目标价，仍必须按平台强制档报名，但要在审核表和日报中标记 `below_target_due_to_platform_forced_discount`，不能把它当作正常达标价。

说明：用户在审核表 `修改意见/备注` 中给出的本期要求，只在转换成 `marketing-price-overrides-YYYY-MM-DD-approved.json` 后作为本批次逐行覆盖价执行；除非用户明确要求“同步进长期规则”，不要直接改写上方全局固定价 / 利润率规则。

## 本期有效策略与巡检口径

日报和自动巡检的目标不是用统一利润率“抓低价”，而是确认真实价格栈是否符合本期已经批准的策略。因此巡检基准必须按以下顺序读取：

1. 当前生效或待生效批次的 `selection-plan + price-overrides`，且必须带活动 ID、店铺、SKC、`finalTargetPrice`、`couponFactor/combo` 和可解释的生效窗口。
2. 用户在本期审核表备注中确认的逐行覆盖价、指定固定价、指定利润率或临时例外。
3. 长期全局规则（默认利润率、曝光前五、清货底线、新品保护等）。

如果用户本期明确批准某个货号按 `15%` 利润率、某个固定最终成交价或某个特殊活动组合执行，只要该策略已经进入当前覆盖文件，巡检应把它标为 `expected`，不得每天按旧的 `30%` 默认利润率或历史 `ALL-ready` 计划重复报警。只有以下情况才应进入 blocker：

- 订单商品行 `currencyPrice` 低于当前有效策略派生的 `finalTargetPrice`（超过 `1 SAR` 容差）。
- 旧普通活动、限时折扣、优惠券或平台强制折扣把最低有效基准价拉到当前策略目标以下。
- 当前策略文件缺失、过期、同一 `storeKey + skc` 有冲突目标价，或缺少 `couponFactor/combo`、活动窗口等判断必需字段。
- 用户备注只停留在人工表格中，尚未转换成本期覆盖文件；此时系统应报告“计划未刷新 / 策略未落盘”，而不是把低利润本身判为错误。
- 新链接 / 新 SKC 动作卡必须使用当前最新已执行的全量计划。若 guard 选中了旧 `all-934`、旧 `ALL-ready` 或其它历史批次计划，产生的“缺精确计划 / 需要兜底”候选只能视为计划选择错误线索；先修正计划选择并重跑 guard，不能把这些候选直接当作真实限时折扣执行清单。

换句话说，`15%` 利润率可以是本期被批准的正常策略；异常只来自“实际成交价低于这版 15% 目标”或“系统还没有读到这版 15% 策略”。

## 一、用户指定固定价规则

> 这些货号先按指定基准价，再做小幅随机浮动：
>
> - 下浮 `2 SAR`
> - 上浮 `1 SAR`

## 三点零、曝光前五链接利润率差异规则

- 数据源：`config/marketing_pricing_policy.json` + BI `storeLinks/links` 中的 `c30_eps_uv -> c7_eps_uv -> eps_uv` 正曝光字段；按 `standard_goods_sn` 全局分组，跨所有店铺、所有链接取同一标准货号曝光量排名前五的 SKC。不能用销量、页面顺序、全 0 指标或 SKC 字典序冒充曝光排名。
- 规则只作用于利润率型自动定价；`row-level override`、本期用户确认价和固定最终成交价优先。
- 基础目标利润率 `> 15%` 时：曝光前五链接目标利润率 = `max(15%, 基础目标利润率 - 5个百分点)`，其他链接保持基础目标利润率。例如基础 `30%` 时，前五按 `25%`、其他仍按 `30%`。
- 基础目标利润率 `<= 15%` 时：前五链接保持 `15%` 底线，其他链接提高到 `20%`。例如清货底线本来只有 `15%`，不能把前五继续降到 `10%`。
- 若同货号没有任何正曝光数据，脚本不得猜测前五，保持基础利润率并在审核表标出曝光数据缺失。
- 若同货号已有正曝光排名、但当前 SKC 不在榜内，则按“非曝光前五”保守口径处理，并在明细里标出未命中曝光榜。
- 审核表必须展示“全局曝光前五 SKC、是否命中、前五目标利润率、其他链接目标利润率”，让用户能复核为什么同货号不同链接价格不同；展示 SKC 时必须带店铺前缀，说明这五个链接来自哪些店铺，而不是给每个店铺各算一组前五。

## 三点一、新品保护价规则

- 刚到仓不久、且全店/多店上架不足约 `30` 天的新品，不按库存沉淀清货价处理。
- 本轮新增保护：这类新品按各店不同的 `23% ~ 26%` 目标利润率反推活动价，硬底线为 `20%`。
- 若货号同时命中上方“固定价”或“用户指定利润率”规则，必须优先执行用户指定规则；新品保护价 / 清货候选价不得覆盖用户点名规则。
- 若活动页存在 `VIP档`，必须优先满足 `VIP档` 的平台最低降幅；但填报后仍要复核是否明显低于 `20%` 利润率。
- 当前保护价明细输出到 `outputs/reports/marketing-new-arrival-protected-prices-2026-05-12.md`，本期覆盖文件为 `outputs/reports/marketing-price-overrides-2026-05-12.json`。

## 三点二、库存沉淀 / 清货候选规则

- 若商品已有在仓剩余库存，且库存去化周期 `> 6` 个月，按 `15%` 利润率报。
- 若商品已有在仓剩余库存，且库存去化周期 `> 3` 个月且 `<= 6` 个月，按 `23% ~ 27%` 利润率随机报，每个店铺可有差异。
- `15%` 是自动填报硬底线；低于 `15%` 的价格不自动填，除非用户单独点名允许。

## 四、成本来源规则

- 成本来源以当前正式成本链路为准：
  - 正式成本文件：`inputs/costs/成本.xlsx`
  - 营销活动成本映射：`tmp/mbrs/marketing-cost-map.json`
  - 营销活动成本映射生成脚本：`scripts/marketing/build_marketing_cost_map.py`
  - BI 导入脚本：`scripts/import_product_costs.mjs`
- 若货号缺完整成本，自动化不得擅自猜价，必须保留给用户确认。
- 营销活动用的仓储费/件必须来自 BI `profit.productStorageDaily`：
  - 使用当前仍在仓库存的移动平均累计仓储成本。
  - 每日仓储费加入该货号“库存仓储成本余额”。
  - 如果当日仓储数量比上一日减少，减少的数量视为已出库/已不再产生仓储费，并按上一日平均仓储成本从余额中剔除。
  - 新增库存只从入仓后开始承担仓储费，不分摊入仓前的历史仓储费。
  - 禁止用 `profit.products.storage_fee_sar / profit.products.quantity`，因为这里的 `quantity` 是历史销量，会把慢销品仓储费/件夸大几十倍。
  - 若 ET 明细有仓储而确认表显示 `0` 或空，视为系统错误；不得按 0 仓储通过。
- 对于缺“头程运输费金额”的批次：
  - BI 会保留批次记录
  - 但不参与完整单位成本均摊
  - 营销活动成本映射也默认跳过这类不完整批次

## 五、平台折扣与页面回写

- 若平台最低折扣要求更严格，则以平台允许的最高活动价为准。
- 计算方式：

`平台允许最高活动价 = 当前价格 × (1 - 最低折扣要求)`

- 若自动算出的目标价高于平台允许上限，则强制压到平台上限。
- 页面若因整数折扣、平台规则或前端联动而回写活动价：
  - 以页面最终实际显示值为准
  - 但必须记录“脚本目标价 / 页面实际价 / 实际降幅”

## 七、限时折扣专项规则

限时折扣是商家可随时设置和取消的价格工具，定位是“填补营销活动空档”，不是在已有营销活动上继续压价。

长期规则（`config/marketing_pricing_policy.json` 也保留同口径机器可读配置）：

- 计划内可报链接原则上必须有一个可解释的限时折扣状态：要么已有不干扰目标价的限时折扣，要么取消/修改旧折扣后重建新的限时折扣；不能因为旧折扣取消过就把该链接永久跳过。
- 默认限时折扣为 `15%` 折扣（即 `当前售价 × 0.85`），但 `15%` 只是默认起点，不是机械套用。
- 核心校验永远是目标成交价：先按时间窗口取 `min(当前售价, 普通营销活动价..., 限时折扣价...)` 作为最低促销基准价，再叠加优惠券测算。`限时折扣价 × couponFactor` 只能表示“限时折扣作为兜底层时”的结果；若普通营销活动价已经更低且可叠券，限时折扣价偏高不会影响最终价，不得据此要求改限时折扣。若普通营销活动缺失或未覆盖，限时折扣才承担兜底调价责任。
- 当普通营销活动报名漏掉且报名期已结束时，限时折扣可以作为兜底补救：限时折扣价应等于原本计划的普通营销活动价，再配套 `15%` 优惠券实现原目标最终价；结束时间必须对齐漏报活动窗口，等下期普通活动恢复后再回到“普通活动 + 优惠券”为主。
- 如果一个链接已有生效/未来生效限时折扣，先判断它是否干扰本期目标价；会干扰就取消或修改，再按新目标重建。一个链接不能同时依赖多个互相冲突的限时折扣。

- 没有普通营销活动生效、也没有即将生效活动覆盖的新品/新链接，可以用限时折扣先把价格降到目标成交价；限时折扣结束时间必须早于下一档普通营销活动生效时间，或在营销活动生效前改为更高的兜底价。
- 新品/新链接进入价格栈前必须先有精确 `storeKey + skc` 计划。`standard_goods_sn` 相同只能说明可能是同款候选，不能自动继承老链接的活动价、限时折扣、优惠券或底价；同货号新 SKC 必须先人工确认成本、仓储费、底价和活动窗口。
- 新链接缺 `finalTargetPrice`、`couponFactor`、成本或被标为 `excluded` 时，只能进入“待定价/待确认”队列，不得生成 `15%` 券报名 dry-run；`couponFactor=1` 或备注明确不叠券/禁券时同样禁止补券。
- 已有普通营销活动生效或未来窗口重叠的商品，限时折扣必须高于该窗口的最低普通营销活动价；推荐的 `85折` 只能作为“高于营销价的兜底折扣”，不能机械套用。如果 `当前售价 × 85%` 低于普通营销活动价或导致叠券后低于利润红线，则不得设置 `85折`。
- 已报名优惠券的商品，限时折扣也要按“限时折扣价 × (1 - 优惠券折扣率)”测算最终价；只看限时折扣本身不够。
- 新一期活动报名前必须盘点现有和未来限时折扣。若发现旧限时折扣与新营销活动/优惠券重叠后会成为最低价，优先方案是：先在审核表列出风险，用户确认后再取消旧限时折扣或改为更高价格；本阶段不得自动取消。
- 若用户决定重做限时折扣，推荐流程是：
  1. 导出现有限时折扣清单和涉及 SKC。
  2. 按时间窗口计算与普通活动/优惠券叠加后的最低价。
  3. 对高风险旧折扣生成“取消/改价建议表”。
  4. 用户确认后，先取消或调高旧折扣，再按新规则设置新的空档期限时折扣。

## 八、优惠券活动专项边界

优惠券活动与普通营销活动报名不是同一条入口，不得直接复用普通活动页的预填假设。

- 已验证活动 `34810 / 平台优惠券招商活动` 的正确入口是：
  1. 先进优惠券详情页 `#/mbrs/marketing/coupon/detail/34810`

### 2026-06-14 修正后的长期规则：`allowed15` 只代表可选流量券，不再代表价格保障券

2026-06-04 低价成交复盘曾确认：优惠券执行器不能把 `MULTI_LEVEL_RULE_GOODS` 的“15% 可报集合”或普通活动 selection plan 直接当成应报目标。`可报` 只表示平台允许报名。

2026-06-14 又确认了更关键的事实：优惠券不是每单必然触发，所以 `couponFactor≈0.85` / `普通活动 + 仅15%券` 这类历史口径不能再证明成交价一定达到券后目标。后续 `allowed15` 只能表示“明确批准的可选流量券目标”，不能表示“为了达成目标价必须补的配套券”。

长期规则如下：

1. **目标集合**
   - 15% 优惠券目标不能再直接等同 `ordinary selection-plan`，也不能仅由 `couponFactor≈0.85` 推导。必须先读取 paired `price-overrides`，由共享 classifier 派生 `allowed15`：
     - 只有 combo / note / `couponPurpose` / `couponPolicy` 等字段明确写明“可选流量券、引流、高曝光支持、曝光 Top5、滞销、高库存、清货、试验”等用途，才允许进入 15% 券计划。
     - `couponFactor≈0.85` 但只写“仅15%券 / 普通活动 + 15%券 / 券后目标价”的历史价格保障口径，必须归类为 `price_guarantee_coupon_blocked`，默认不得补券。
     - `couponFactor=1`、combo 含 `不叠券` / `券都禁止` / `15/30/50%券都禁止`，必须排除。
     - `couponFactor` 缺失、combo 空、缺 price-overrides、同一 `store+skc` 多活动口径冲突，一律 fail closed，不自动报名。
   - `MULTI_LEVEL_RULE_GOODS` 中不在 `allowed15` 计划里的 SKC，属于“可报但不应报”，不能自动报名。
   - `MULTI_LEVEL_RULE_ENROLLED_GOODS` 的 active 已报集合最终必须符合 `allowed15` 计划；允许的终态是：
      - 价格保障券 active 数为 `0`；
      - 明确批准的可选流量券 active 数与当前流量券计划一致；
      - `禁止/未知仍 active 数 == 0`
      - `active 但不在 allowed15 流量券计划数 == 0`
2. **提交脚本安全闸**
   - `scripts/marketing/submit_coupon_activity_goods.mjs` 默认必须传 `--target-plan`。
   - 默认执行模式必须是 `coupon-allowed15-intersection-15pct-available`，但这里的 `allowed15` 已是“可选流量券”集合；不能退回 `all-15pct-available`，也不能退回普通活动 plan 全量交集。
   - `--allow-all-15pct-available` 原则上禁用；只有用户单独确认“本次就是独立全量引流券实验”并且预算、底价、触券下探利润均通过，才可作为一次性人工覆盖。
   - `2026-06-05` 起，提交脚本默认会 live 读取当前/未来仍有效的限时折扣活动；目标 SKC 如果仍在 active/future 限时折扣里，限时折扣扫描只能先给出兜底层测算。最终是否低于/命中/高于目标，必须合并同一时间窗口的普通营销活动价、当前售价和限时折扣价，用“不含券的最低促销基准价”对比 `finalTargetPrice`。优惠券只额外计算触券下探风险，不能用来证明目标成交价达标。
   - `--allow-limited-discount-overlap` 只能作为已逐 `SKC` 复核的人工临时覆盖；默认策略仍是价格栈守卫。任何覆盖都要在输出里保留 `effectiveBasePrice/effectiveBaseSource/couponFactor/effectiveFinalWithCoupon/targetFinalPrice/diff`；如果只有限时折扣价证据，必须标记为兜底层候选而不是最终成交价结论。
   - 如果本期计划内 SKC 因旧限时折扣被价格栈守卫排除，默认补救顺序是：先确认不含券保底价是否低于/高于目标价；若低于，取消或修改旧限时折扣；若高于，则用普通活动或新的限时折扣兜底到目标价。不得把补报优惠券作为价格保障补救。
   - 提交脚本还必须加载最新 `marketing-stack-review` 和旧普通活动填报价证据；活动扫描超过 48 小时、stack review 不可用、旧活动价证据目录缺失/解析失败，或目标 SKC 有旧普通/度假季标签但没有旧活动价证据时，写路径 fail closed，不提交。缺证据的下一步是系统只读查价/刷新叠加审核，取不到才报告登录、接口或店铺身份阻塞。提交器遇到登录页或券集合接口 `20302` 时，也要先用真实鼠标点击登录/继续登录并重试，恢复失败才停止为登录阻塞。

   - `scripts/marketing/export_marketing_stack_review.mjs --coupon-target-plan <plan.json>` 会输出 allowed15 配套计划校验列；可额外传 `--coupon-price-overrides <price-overrides.json>` 明确覆盖价来源。遇到 MBRs `20302 子系统登录重定向` 时，脚本会进入登录页并用真实鼠标点击登录/继续登录后重试；仍失败才把具体店铺列为登录阻塞。
   - 叠加审核的 BI 标签上下文默认应使用云端权威快照：`--cloud-bi-ssh shein-bi-tencent --cloud-bi-root /opt/shein-bi/app`，或显式 `--bi-portal-data <data.json>`。输出必须记录 `source.biGeneratedAt / biDataPath / biDataTransport / biFallbackUsed`；不得把本地灾备 `outputs/bi-portal/data.json` 当成实时云端事实。

   - 优先看 `15%券档active是否符合允许计划`、`15%券档允许配套计划数`、`15%券档禁止/未知仍active数`、`15%券档active但不在允许计划数`。
   - `15%券档剩余未入已报集合数` 是“平台可报但未报”的集合，不等于本期应报目标；如果配套计划已覆盖，这个数大于 0 是正常现象。
4. **取消误报**
   - 多档券已报名商品页是 `#/mbrs/marketing/coupon/rule/goods/{activityId}/{levelRuleId}`。
   - 取消接口是 `/mrs-api-prefix/mbrs/activity/multi-level/partake/cancel`，不是普通活动的 `batch_cancel_partake_goods` / `cancel_activity`。
   - payload 必须来自已报集合里的真实字段：
      - `partake_good_id`
      - `partake_level_rule_id`
      - `partake_rule_good_id`
      - `skc`
   - 取消脚本的“不能误取消”保护集必须是共享 classifier 的 `allowed15`，不是普通活动 selection plan；`allowed15` active 不得被 `riskReason` 绕过。
   - 执行前必须二次加载 coupon classifier plan；任何出现在 `allowed15` 保护集里的 SKC，只有在取消侧重新计算 `最低有效基准价 × couponFactor < targetFinalPrice - 1 SAR` 后才允许作为风险取消目标，否则安全停止。若取消侧只有限时折扣价证据、缺普通营销活动/当前售价证据，必须 fail closed，不得真实取消。

   - `scripts/marketing/scan_coupon_old_ordinary_overlap_risks.mjs` 是旧普通营销活动叠券只读观察入口；旧普通活动重叠本身不得生成可执行取消清单，必须补齐价格栈证据后再进入取消流程。
