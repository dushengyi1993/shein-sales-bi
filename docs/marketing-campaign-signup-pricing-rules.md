# SHEIN 营销活动报名价格规则

本文是**业务政策**：决定什么价格、优先级与安全线。实际操作入口见 [marketing-daily-inspection-handoff.md](marketing-daily-inspection-handoff.md)，执行步骤见 `skills/shein-marketing-ops/SKILL.md`；两者不得用历史运行记录替代本政策。

## 三类活动优先级（2026-06-21）

1. **普通营销活动必报，优先级最高。** 只要活动仍可报、商品符合本期策略、平台允许报名，就先报普通营销活动；限时折扣已覆盖或当前售价达标，都不能替代普通活动。
2. **限时折扣也必报，但只是兜底。** 没有普通活动时直接兜目标价；有普通活动时默认 `15%`，若低于目标价/底价/利润线就缩浅折扣或兜到目标价。限时折扣缺口可以自动修复，但不能因此忽略普通活动漏报。
3. **优惠券只做小批量流量实验。** 只允许明确批准的高曝光、滞销高库存或清货试验；不能作为目标价保障。若券会和普通活动/限时折扣叠加打穿目标或安全线，要取消/排除券。
4. **执行和巡检顺序：** 普通营销活动漏报/待报 → 限时折扣缺口/错价 → 优惠券实验冲突。
5. **结构覆盖和价格覆盖分开验收。** 限时折扣兜住目标价不代表普通营销活动已报；普通营销活动已报也不代表限时折扣兜底已报。
6. **优惠券冲突时券让路。** 若实验券触发后会低于目标价或安全线，取消/排除券，不能为了保留券而削弱普通活动或限时折扣。

## 适用范围

- 适用于 SHEIN 商家后台“营销活动报名”里的活动填报。
- 也适用于报名前的优惠券、限时折扣和既有营销活动叠加风险审核；用户明确要求开始报新活动前，本规则只用于只读审核和生成复核文档。
- 普通营销活动是平台给流量扶持的主活动层：只要商品符合本期策略且仍在报名窗口内，原则上必须报名；报名窗口和活动生效窗口分开判断，不能等生效日才想起来补报。
- 自动化只负责：
  - 勾选商品
  - 填写 `提报的活动价格`
  - 填写 `提报的活动降幅`
  - 滚动复核
- 自动化默认 **不得点击** 最终 `提交报名`；只有用户在本轮明确授权“你自己提交/全自动报完”时才可真实提交，并且提交后必须用后台已报集合回读验证。
- 页面里 `提报的活动价格（实际生效参考此列）` 优先级最高；`提报的活动降幅` 主要用于配合平台校验。
- 若普通营销活动、优惠券和限时折扣存在时间重叠，报名前必须先做“保底成交价 + 触券下探风险”审核，不能只看本次活动价。

## 价格叠加安全红线

已验证风险样本：`2026-06-01` HL 店 `SK-04031胶囊咖啡机` 订单净收入 `183.89 SAR`，商品成本 `182.52 SAR`，不含仓储费利润率仅 `0.74%`；同货号 HL 在 `2026-05-31` 的活动标签同时包含 `SA-超级爆品活动-第42期`、`#HLSDdsy1993#限时折扣#2026-05-03#1` 和 `2026年「度假季」常规活动-全托 半托（本地）`。根因模型是：同一时间多个促销价重叠时，SHEIN 取最低促销价；若商品还报名优惠券，则优惠券继续作用在该最低价上。

因此后续所有活动报名必须按以下保守模型审核：

1. 对每个 `店铺 + SKC + 时间窗口`，先列出所有可能生效的价格来源：
   - 当前原始价 / 划线价 / 当前售价
   - 已报名、已生效、未来将生效的普通营销活动价
   - 本地已知普通活动填报价证据（例如 `tmp/mbrs/deadline-fill-results/*.json` 中仍在生效窗口内的填报价）
   - 已设置、已生效、未来将生效的限时折扣价
   - 已报名或计划报名的优惠券活动、券档、预算和生效范围
2. 对每个时间窗口计算最低促销基准价：

   `最低促销基准价 = min(当前售价, 普通营销活动价..., 限时折扣价...)`

   同一 `SKC` 若存在多条已生效或未来生效的限时折扣，必须按该时间窗口内 **最低** 的 `limitedDiscountPrice` 判定风险，不能取第一条、最新一条或活动列表顺序。

3. `2026-06-14` 起优惠券不是每单必然触发，不能再作为保底成交价层。必须拆成两套价格：

   `保底成交价 = 最低促销基准价`

   `触券下探价 = 最低促销基准价 × (1 - 商家承担优惠券折扣率)`

   保底成交价用于判断买家不触券时是否仍达到本期 `finalTargetPrice`；触券下探价只用于判断“如果券触发，会不会低于底价/利润红线”。若优惠券状态、券档或预算不确定，只能按风险线索处理，不能用“假定有券”证明价格达标。

   **禁止仅凭活动标签做真实取消或报名。** `度假季`、旧普通活动、旧限时折扣、优惠券标签都只能生成风险候选；真实动作必须继续比较保底成交价、触券下探价与本期目标/底线：

   - 若 `保底成交价 < finalTargetPrice`（超过平台取整/`1 SAR` 容差），说明活动层本身低于目标价，应取消或调高最低且可控的活动层，必要时临时下架止损。
   - 若 `保底成交价 ≈ finalTargetPrice`，说明普通活动价或限时折扣价本身能保障目标成交价。
   - 若 `保底成交价 > finalTargetPrice`，说明价格偏高；应补齐普通营销活动或用限时折扣兜底到目标价，不能靠优惠券“算下来”。
   - 若 `触券下探价` 低于底价/利润线，即使保底价达标，也不得把该 SKC 放进 15% 券，除非用户单独确认清货亏本试验。
   - 历史“普通活动 + 仅15%券”计划必须迁移：取消作为价格保障的优惠券，改由普通活动价或限时折扣价直接命中目标。
   - 若旧普通活动填报价证据显示旧普通活动价本身低于目标，或触券下探价会打穿底线，必须先阻断优惠券提交/日报 no-action；这类证据即使来自旧填价文件而非当前提交器，也不能忽略。
   - 若商品存在旧普通活动标签但缺旧普通活动价证据，不能当作安全，也不能把“缺证据”丢给用户；系统必须自动触发只读取证（live 扫描 / 后台回读普通活动已报商品价）。只有登录失效、店铺身份不确定、平台接口不可达等系统取不到证据的情况，才报告具体阻塞。
   - 若脚本使用 `--allow-limited-discount-overlap` 这类人工覆盖参数，必须有逐 `SKC` 的价格证据；该参数只能临时用于已审核补救，不得作为默认自动化策略。
4. 利润率必须同时展示两套：

   `商品利润率 = (保底成交价 - 商品完整成本) / 保底成交价`

   `含仓储费利润率 = (保底成交价 - 商品完整成本 - 仓储费摊销/件) / 保底成交价`

   若本行允许 15% 流量券，审核表还要额外展示“触券下探利润率”，用于判断引流是否会打穿底线。

5. 安全判断默认以 `含仓储费利润率` 为主；若仓储费缺失，审核表必须标记 `仓储费缺失/估算缺失`，不得把仓储费按 0 当成已安全。
6. 普通商品默认目标仍按 `30%` 左右利润率；新品/正常品报名前的含仓储费利润率原则上不得低于 `20%`。库存沉淀清货可以按 `15%` 含仓储费利润率作为低价底线，但必须在审核表标红并由用户逐项确认；低于 `15%` 的最终成交价禁止自动报名，除非用户在备注栏单独点名确认。
7. 固定价规则里的固定价从此按“目标最终成交价”理解，不再默认等于“普通活动价”。如果还叠加 `15%` 优惠券，应反推普通活动价；如果已有更低旧活动或限时折扣，则固定价目标视为失效并进入高风险复核。
8. 同一标准货号在所有店铺、所有链接中按 BI 曝光量取全局前五链接；这五个链接可以比其他链接低 `5` 个百分点目标利润率，但不得低于 `15%` 底价。如果基础目标利润率本来就是 `15%`，前五链接保持 `15%`，其他链接提高到 `20%`，避免把底线继续向下打穿。不能按单店拆出多个“前五”。
9. 固定价和逐行覆盖价优先于曝光前五规则；曝光前五只调整利润率型自动定价，不能覆盖用户在本期审核表里确认的具体价格。

### 2026-06-21 修正：BI 不是报名证据，限时折扣是必报价格层

BI 只能告诉我们“哪些链接在卖、有哪些订单价格、曝光和库存线索”，不能证明营销后台真的报了普通活动或限时折扣。后续巡检和补救必须按下面证据链执行：

1. **是否已报普通活动 / 限时折扣 / 优惠券，只认 SHEIN 后台 live scan/readback。** BI 标签、历史计划文件、历史提交成功提示只能作为线索，不能输出 no-action。
2. **每日巡检必须有 live 覆盖。** 只读审核和最终 19 店回读由云端 session HTTP/live scan 为主；真实报名写入默认使用本机后台 headless 店铺 profile，不弹可见前端、不抢焦点。跨店默认 4 个独立 profile 一批，负载高或 profile 不稳时降为 3 个；批内跨店并行，同店操作链严格串行，且 profile、端口、临时目录、救援文件和可变输出不得共享。单店失败不得拖住同批其他店；全批终态后逐店清理并验证进程、端口、租约为 0。每日长期授权限时折扣和每周已授权普通活动都适用该边界；只有本机不可用且当天必须闭环时才启用受控云端浏览器 fallback，云端每段最多 1 店/1 组。
3. **限时折扣是所有在售运营链接必备层。**
   - 没有当前或即将生效普通活动：限时折扣直接兜到 `finalTargetPrice`。
   - 有当前或即将生效普通活动：也要有默认 `15%` 限时折扣。
   - 若默认 `15%` 折后价低于 `finalTargetPrice` 或底价/利润安全线，就缩浅折扣比例，保证限时折扣价不低于目标价。
   - 已有不同价格的限时折扣不能无脑自动覆盖：若该活动只包含目标 SKC，可在 dry-run 安全后修改或结束重建；若混有计划外 SKC、疑似人工特殊价、或活动归属不清，必须阻断并列人工确认清单。
   - 若平台最低折扣要求导致“既要有折扣、又不能低于目标价”无法同时满足，禁止自动写入，日报列为平台规则阻断。
4. **新链接 / 新 SKC / 活动页新增可报行必须自动进入处理。** 不能只写“待定价”后结束：若能从最新已执行全量计划、同一标准货号全局曝光 Top5 规则、成本/仓储费/底价推导出安全目标价，就生成限时折扣 rescue，dry-run 安全后自动执行并回读；只有缺成本、缺目标价、缺仓储费/底价、库存不足、平台规则或登录身份阻断时，才列具体阻断，不硬报。
5. **普通活动漏报仍分授权处理。** 若用户已授权该活动自动报，按既有分批报名流程提交并回读；未授权时给人话方案和阻断/截止时间提醒。
6. **活动最低库存只允许事务式临时补量。** 普通营销活动或限时折扣报名时，平台真实最低库存只认活动 live 页面、`query_goods` 或 dry-run，BI `platform_saleable_stock` 仅作线索。提交前在同一 `store + SKC/SKU` 库存锁内记录 `totalUsableInventory / totalInventoryQuantity / totalLockedQuantity`；可用库存不足时，只临时补到平台要求的精确最低可用库存。提交及 live readback 后，无论成功失败都在 `finally` 立即恢复报名之前的原可用库存，并按恢复时实时锁定/不可用量计算覆盖量。
7. **临时补量必须恢复后再验收。** 恢复后同时回读库存和活动报名状态；恢复失败、恢复后活动失效/被平台撤销，或锁定量变化导致无法精确恢复原可用量，均 fail closed，不能写成功。即使 ET 当日运营可售库存 `<= 10`，也只允许在报名事务短窗口内临时补到平台最低值，随后恢复库存巡检给出的实盘分配；该短窗口存在订单与超卖风险。此授权取代“普通活动库存虚增不授权”和“平台活动库存下限高于用户指定数量一律阻断”，但不授权永久增库存、优惠券补库存或脱离报名事务的库存修改。
8. **旧持久补量执行器不得承接新授权。** 执行结果若不能提供平台最低值来源、补量前三字段快照、锁、临时写入、报名回读、`finally` 恢复及恢复后双回读证据，必须以“执行器能力未就绪”阻断，禁止调用旧 ET 门控永久补量路径。
9. **实现入口固定。** 报名库存写入统一由 `lib/marketing_activity_inventory_transaction.mjs` 调度、`lib/marketing_activity_inventory_openapi.mjs` 读写实时库存，并由普通活动和限时折扣 integration wrapper 把报名提交及 enrollment readback 包在同一 `try/finally` 生命周期内。旧 `manage_manual_limited_discount_inventory.mjs` 仅保留历史 dry-run/决策兼容，真实执行永久禁用。

### 2026-08-02 修正：ET 低库存畅销货号的新活动价格收回

该规则只作用于新报名、补报、重建普通活动或限时折扣，不追溯改写正在正常运行的旧活动：

1. 触发条件同时满足：ET 当天已匹配运营可售库存 `<= 10`，且同一标准货号跨 19 店近 30 天有效销量合计 `> 30`。
2. 价格按“档位上移一级”处理，不机械把页面折扣率减少 5%。同标准货号跨 19 店、全部链接的最新 7 天曝光 Top5，恢复为该货号普通链接的最新已批准价格；普通链接则在普通链接目标利润率基础上提高 5 个百分点重新算价。
3. 平台最低折扣或最高允许报名价优先，能收回多少收回多少；商品成本、底价和利润安全线仍是硬门禁。
4. ET 恢复到 `> 10` 后，后续新活动恢复原批准价格档位；这次收回不得写回或污染“最新已批准基准”。
5. 价格决策优先级固定为：ET 低库存畅销品收回折扣 > 自动高点击专属折扣 > 新链接/新品 Top5 待遇 > 普通活动基准。已登记人工特殊折扣不自动覆盖，单独列给用户审核。
6. Top5 口径仍是同一标准货号跨 19 店、全部链接的最新 7 天曝光；30 天销量口径是标准货号跨 19 店有效销量汇总，不是单链接销量。
7. Top5 收回价按标准货号统一：读取最新批准全量 baseline 中该标准货号的普通链接档批准价，同一货号跨店统一恢复，不再要求同一 `store + SKC` 存在单店历史价。缺该标准货号统一普通档价时才 fail closed。
8. ET 当天完整库存快照省略零库存商品时，必须继续读取 ET 09 散件仓最新库存流水；若该货号最新余额明确为 `0`，按“当天已匹配、运营可售 0”处理。货号仅因是否带中文品名产生差异时按标准货号代码归并，不能报成 ET 未匹配。

## 报名前审核文档要求

每次报活动前必须先生成给用户复核的审核文档；用户确认前不得报名新活动、不得批量取消或重报限时折扣。审核文档至少包含以下字段：

| 字段组 | 必填字段 |
| --- | --- |
| 商品定位 | 店铺、分组、活动 ID/名称、SKC、SKU、供方货号、标准货号、商品标题/中文名 |
| 时间窗口 | 报名截止、普通活动开始/结束、优惠券开始/结束或活动期、限时折扣开始/结束、是否与既有活动重叠 |
| 原始价格 | 原价/划线价、当前售价、SHEIN 页面/API 价格字段来源、平台最低降幅 |
| 成本 | 商品完整成本、仓储费摊销/件、含仓储费成本、仓储费口径、成本缺失/仓储费缺失标记 |
| 本次建议 | 建议普通活动价、建议普通活动折扣、建议限时折扣价/折扣、是否使用可选 15% 流量券 |
| 价格测算 | 最低促销基准价、保底成交价、触券下探价、商品利润率、含仓储费利润率、最低价来源 |
| 风险提示 | 旧活动重叠、限时折扣更低、优惠券可叠加、平台最低折扣压价、预算异常、利润率低于红线、缺成本/缺仓储费 |
| 用户复核 | 修改意见/备注、用户确认动作、是否允许低于默认红线、是否需要取消旧限时折扣 |

审核文档应同时提供“明细行”与“按标准货号汇总”两种视图：明细行用于逐 SKC 防漏，汇总视图用于用户快速看价格区间和风险。用户在 `修改意见/备注` 中确认后，才能转换成本期覆盖文件；覆盖文件必须保留用户备注来源。

用户确认后不能只靠文件名里的 `approved` 继续执行。必须用 `scripts/marketing/lock_ordinary_campaign_execution_plan.mjs` 把用户批准原话、批准来源、selection/price payload hash、输出文件 SHA-256 和 work fingerprint 固化到 `approval-manifest-*.json`。候选 subset 不携带执行授权；store/chunk/singleton 批量提交器只接受与 manifest 完全一致的已批准文件，授权后任一改动或跨 fingerprint resume 都失败关闭。

### 用户确认方案的固定输出格式

给用户看的方案必须是 Excel 工作簿（`.xlsx`）为主，Markdown 只做摘要入口，JSON/CSV 只给脚本和复核使用。不能只给用户一张几百行明细表，也不能只给 CSV/JSON。

工作簿至少包含：

| Sheet | 作用 | 必填内容 |
| --- | --- | --- |
| `说明` | 告诉用户本方案能不能直接报、哪些动作未执行 | 数据日期、活动范围、候选数、可报数、剔除数、是否真实提交、后续执行边界 |
| `按货号汇总` | 用户主审入口，一行看懂一个标准货号 | 标准货号、商品名、活动 ID 分布、覆盖店铺数/SKC 数、预期利润率、预期最终价区间、普通活动填报价区间、是否使用可选 15% 流量券、触券下探价区间、曝光前五口径、缺 7 天曝光原因、剔除/阻塞摘要、备注 |
| `店铺差异明细` | 解释同一货号不同店为何价格不同 | 店铺、SKC、活动 ID、当前售价、平台最低降幅、目标利润率、曝光排名/是否前五、普通活动价、最终成交价、仓储费、利润率、差异原因、备注 |
| `报名明细` | 执行 allowlist，防漏报/错报 | 店铺、活动 ID/名称、SKC、标准货号、提报活动价、提报折扣、`finalTargetPrice`、`couponFactor/combo`、价格来源、是否提交、备注 |
| `剔除项/阻塞项` | 说明为什么不报 | 店铺、SKC、标准货号、剔除原因、缺成本/缺仓储/平台状态/库存/货号待归并/低于底价/缺覆盖价等证据、下一步、备注 |
| `低价补救/风险项` | 把当前风险和本次报名分开 | 店铺、SKC、标准货号、订单成交价或最低基准价、目标价、差额、风险来源、已处理/待观察/需授权动作、备注 |
| `15%券流量试验计划` | 可选流量券方案，不承担价格保障 | 店铺、SKC、标准货号、普通活动填报价/限时折扣保底价、券活动 ID、`couponFactor=0.85`、保底成交价、触券下探价、使用理由（高曝光/滞销/清货）、预算建议、禁止 30%/50% 券、执行前检查、备注 |

格式硬要求：

- 除 `说明` 页外，每个 sheet 都必须有 `备注` 或 `修改意见` 列，供用户直接标注。
- `按货号汇总` 必须体现用户关心的业务判断：预期利润率、预期价格、曝光前五影响、是否配优惠券、剔除项原因；不能只列店铺/SKC/活动价。
- 同一标准货号在不同店铺方案有差异时，必须能在 `店铺差异明细` 里看到差异来源（曝光前五、平台最低降幅、当前售价、成本/仓储、固定价/指定利润率、覆盖价）。
- `15%券流量试验计划` 必须和价格保障动作分开表达：普通活动/限时折扣先保证保底成交价；只有高曝光支持、全店高库存滞销品引流或清货试验才准备可选券。上券前必须刷新预算、旧普通活动、限时折扣和已报集合证据。
- `剔除项/阻塞项` 不是“丢弃清单”，而是后续补证据/补成本/等库存/等平台状态恢复的动作来源。
- 给用户的摘要必须按货号说人话：例如“此货号可报多少店、目标利润率是多少、前五链接怎么处理、是否配 15% 券、哪些店不同、为什么剔除”。不要把 800 行明细直接丢给用户当主方案。

## 报价优先级

1. 本期用户确认表 / 备注生成的逐店铺 + 活动 + SKC 覆盖价（row-level override）
2. 用户指定固定价
3. 用户指定利润率
4. 新品保护价
5. 库存沉淀 / 清货候选价
6. 默认利润率规则
7. 平台活动强制档位 / `VIP档` 最低降幅 / 页面回写结果复核（作为最终硬约束记录）

平台最低降幅不是固定 `10%`：大多数活动可能要求 `10%`，少数活动可能要求 `5%`，也可能存在 `VIP档`。执行时必须读取活动页/API 的实际最低降幅或 VIP 档位；若 `VIP档` 强制导致价格低于本期目标价，仍必须按平台强制档报名，但要在审核表和日报中标记 `below_target_due_to_platform_forced_discount`，不能把它当作正常达标价。

说明：用户在审核表 `修改意见/备注` 中给出的本期要求，只在转换成 `marketing-price-overrides-YYYY-MM-DD-approved.json` 后作为本批次逐行覆盖价执行；除非用户明确要求“同步进长期规则”，不要直接改写上方全局固定价 / 利润率规则。

## 本期有效策略与巡检口径

日报和自动巡检的目标不是用统一利润率“抓低价”，而是确认真实价格栈是否符合本期已经批准的策略。因此巡检基准必须按以下顺序读取：

1. 当前生效或待生效批次的 `selection-plan + price-overrides`，且必须带活动 ID、店铺、SKC、`finalTargetPrice`、`couponFactor/combo` 和可解释的生效窗口。
2. 用户在本期审核表备注中确认的逐行覆盖价、指定固定价、指定利润率或临时例外。
3. 长期全局规则（默认利润率、曝光前五、清货底线、新品保护等）。

### 方案基准和整数价微调

- 后续每次做新一轮普通营销活动方案，必须以上一次用户确认并真实执行或等待执行的最终版 `selection-plan + price-overrides` 为基准，继承其中的用户备注、固定价、特殊利润率、低于默认红线但已确认可报的例外、货号归并和小数微调。
- 新一轮云端 BI / 后台 live scan 只用于补充变化：新增链接、新增可报 SKC、曝光 Top5 变化、平台最低降幅、成本/库存变化、活动窗口变化和旧证据失效。不能因为重新扫描到新数据，就把已经确认过的上期策略回退为默认 `30%` 或旧草稿。
- 执行方案和 source summary 必须写明本轮继承的 baseline 文件路径；找不到可靠最终版基准时，先报告 blocker，不能直接生成可提交方案。
- 用户确认并提交完成后，必须把本轮最终全量 `selection-plan + price-overrides` 写成下一轮基准：文件里保留 `baselineForNextOrdinaryActivity=true` 和 `baselineForLimitedDiscountFallback=true`，后续普通活动方案、订单审计和限时折扣兜底都读取这对最终文件，而不是读取演示预填、单店 supplement、旧 `ALL-ready` 或未合并草稿。
- 订单审计 `audit_order_prices_against_plan.mjs` 支持 `--links-data`（默认 `outputs/bi-portal/sections/linksData.json`）精确目标价 overlay：先从 linksData 按 `storeKey + SKC` 取当前目标价，再按订单时间 + 活动/窗口选择生效计划行。普通活动报名完成但尚未到活动开始时间时，日报只检查后台已报/待生效、限时折扣兜底和旧活动重叠风险，不把窗口外订单按本期活动价判 blocker；重复计划不再自动报错，只在活跃目标歧义/冲突时报冲突。
- 普通活动填报价不要批量使用整百/整数固定价。固定价或备注价可以在不越过平台价格上限、目标价底线和利润/成本安全线的前提下做几毛钱级别的小数微调，例如 `160` 可填成 `159.57` 或 `160.28`。
- 真实预填/提交前必须检查 `price-overrides` 目标行没有整数价；若仍有整数价，先生成带 `jitter` 标记的修正版，并用修正版预填/提交，不能沿用未微调旧文件。

如果用户本期明确批准某个货号按 `15%` 利润率、某个固定最终成交价或某个特殊活动组合执行，只要该策略已经进入当前覆盖文件，巡检应把它标为 `expected`，不得每天按旧的 `30%` 默认利润率或历史 `ALL-ready` 计划重复报警。只有以下情况才应进入 blocker：

- 订单商品行 `currencyPrice` 低于当前有效策略派生的 `finalTargetPrice`（超过 `1 SAR` 容差）。
- 旧普通活动、限时折扣、优惠券或平台强制折扣把最低有效基准价拉到当前策略目标以下。
- 当前策略文件缺失、过期、同一 `storeKey + skc` 有冲突目标价，或缺少 `couponFactor/combo`、活动窗口等判断必需字段。
- 用户备注只停留在人工表格中，尚未转换成本期覆盖文件；此时系统应报告“计划未刷新 / 策略未落盘”，而不是把低利润本身判为错误。
- 新链接 / 新 SKC 动作卡必须使用当前最新已执行的全量计划。若 guard 选中了旧 `all-934`、旧 `ALL-ready` 或其它历史批次计划，产生的“缺精确计划 / 需要兜底”候选只能视为计划选择错误线索；先修正计划选择并重跑 guard，不能把这些候选直接当作真实限时折扣执行清单。

换句话说，`15%` 利润率可以是本期被批准的正常策略；异常只来自“实际成交价低于这版 15% 目标”或“系统还没有读到这版 15% 策略”。

## 三点零、曝光前五链接利润率差异规则

- 数据源：`config/marketing_pricing_policy.json` + BI `storeLinks/links` 中的 `c30_eps_uv -> c7_eps_uv -> eps_uv` 正曝光字段；按 `standard_goods_sn` 全局分组，跨所有店铺、所有链接取同一标准货号曝光量排名前五的 SKC。不能用销量、页面顺序、全 0 指标或 SKC 字典序冒充曝光排名。
- 规则只作用于利润率型自动定价；`row-level override`、本期用户确认价和固定最终成交价优先。
- 基础目标利润率 `> 15%` 时：曝光前五链接目标利润率 = `max(15%, 基础目标利润率 - 5个百分点)`，其他链接保持基础目标利润率。例如基础 `30%` 时，前五按 `25%`、其他仍按 `30%`。
- 基础目标利润率 `<= 15%` 时：前五链接保持 `15%` 底线，其他链接提高到 `20%`。例如清货底线本来只有 `15%`，不能把前五继续降到 `10%`。
- 若同货号没有任何正曝光数据，脚本不得猜测前五，保持基础利润率并在审核表标出曝光数据缺失。
- 若同货号已有正曝光排名、但当前 SKC 不在榜内，则按“非曝光前五”保守口径处理，并在明细里标出未命中曝光榜。
- 审核表必须展示“全局曝光前五 SKC、是否命中、前五目标利润率、其他链接目标利润率”，让用户能复核为什么同货号不同链接价格不同；展示 SKC 时必须带店铺前缀，说明这五个链接来自哪些店铺，而不是给每个店铺各算一组前五。
- 新上架 7 天内、且尚未报过普通营销活动的链接，虽然不一定真实进入曝光前五，也要临时按“曝光前五力度”处理：
  - 首次报 New Arrivals / 新品 / 超级新品类普通营销活动时，普通活动目标价按前五力度生成，并在明细中单独标 `newListingTopTreatment`，不能误写成“真实曝光前五”。
  - 如果暂时报不上普通营销活动，或普通活动尚未生效，巡检必须立即生成一周限时折扣兜底，限时折扣价同样按前五力度。
  - 已有旧限时折扣但不是一周窗口或不是前五力度的，若旧活动只包含目标 SKC，可以在 dry-run 安全后取消/结束并重报；若旧活动混有计划外 SKC、人工特殊价或无法确认归属，必须阻断并列人工确认。
  - 该规则的机器配置在 `config/marketing_pricing_policy.json` 的 `newListingWithin7Days`，当前窗口为 `7` 天、限时折扣持续 `7` 天。
- 平台新品标签延续：`config/marketing_pricing_policy.json` 新增 `newListingWithin7Days.platformNewLabelPatterns = ["新款", "新品", "New Arrivals", "new arrival"]`。平台标签命中时，即使上架超过 7 天，仍按新品/前五力度待遇，除非该链接已有普通营销活动。
- 目标价证据优先级：先查精确 `storeKey + SKC` 目标价（`exact_store_skc_target_price`），再回退到同标准货号最低批准价。`build_new_listing_limited_discount_plan.mjs --current-marketing-live-scan` 可用 live scan 证明已有限时折扣覆盖，避免重复报名。

## 三点一、新品保护价规则

- 刚到仓不久、且全店/多店上架不足约 `30` 天的新品，不按库存沉淀清货价处理。
- 本轮新增保护：这类新品按各店不同的 `23% ~ 26%` 目标利润率反推活动价，硬底线为 `20%`。
- 若货号同时命中上方“固定价”或“用户指定利润率”规则，必须优先执行用户指定规则；新品保护价 / 清货候选价不得覆盖用户点名规则。
- 若活动页存在 `VIP档`，必须优先满足 `VIP档` 的平台最低降幅；但填报后仍要复核是否明显低于 `20%` 利润率。
- 当前保护价明细输出到 `outputs/reports/marketing-new-arrival-protected-prices-2026-05-12.md`，本期覆盖文件为 `outputs/reports/marketing-price-overrides-2026-05-12.json`。

## 三点二、库存沉淀 / 清货候选规则

- 若商品已有在仓剩余库存，且库存去化周期 `> 6` 个月，按 `15%` 利润率报。
- 若商品已有在仓剩余库存，且库存去化周期 `> 3` 个月且 `<= 6` 个月，按 `23% ~ 27%` 利润率随机报，每个店铺可有差异。
- `15%` 是自动填报硬底线；低于 `15%` 的价格不自动填，除非用户单独点名允许。

## 四、成本来源规则

- 成本来源以当前正式成本链路为准：
  - 正式成本文件：`inputs/costs/成本.xlsx`
  - 营销活动成本映射：`tmp/mbrs/marketing-cost-map.json`
  - 营销活动成本映射生成脚本：`scripts/marketing/build_marketing_cost_map.py`
  - BI 导入脚本：`scripts/import_product_costs.mjs`
- 若货号缺完整成本，自动化不得擅自猜价，必须保留给用户确认。
- 营销活动用的仓储费/件必须来自 BI `profit.productStorageDaily`：
  - 仓储费是标准货号共享货盘成本，不是店铺/SKC 链接级成本；同一标准货号所有店铺链接必须使用同一个仓储费/件。
  - 使用当前仍在仓库存的移动平均累计仓储成本。
  - 每日仓储费加入该货号“库存仓储成本余额”。
  - 如果当日仓储数量比上一日减少，减少的数量视为已出库/已不再产生仓储费，并按上一日平均仓储成本从余额中剔除。
  - 新增库存只从入仓后开始承担仓储费，不分摊入仓前的历史仓储费。
  - 禁止用 `profit.products.storage_fee_sar / profit.products.quantity`，因为这里的 `quantity` 是历史销量，会把慢销品仓储费/件夸大几十倍。
  - 若 ET 明细有仓储而确认表显示 `0` 或空，视为系统错误；不得按 0 仓储通过。
  - 对已入仓但零销量、因此缺少 `profit.products` 商品行的货号，必须用 `inventoryDepletion` 的当前可售量 + 破损量作为数量基数，将该货号 ET 仓储费余额折算为共享仓储费/件；不能因为所有店都没卖而宣称“没有仓储记录”。
- 对于缺“头程运输费金额”的批次：
  - BI 会保留批次记录
  - 但不参与完整单位成本均摊
  - 营销活动成本映射也默认跳过这类不完整批次

## 五、平台折扣与页面回写

- 方案生成阶段若已能读取平台最低档，应把平台允许的最高活动价明确写入方案，连同利润率一起展示。
- 计算方式：

`平台允许最高活动价 = 当前价格 × (1 - 最低折扣要求)`

- 用户批准后，`targetPrice/finalTargetPrice` 保留为审计基准。报名页后来出现更严格的普通档/VIP档，导致平台最低档低于批准价时，不再阻断或重复确认，直接按平台最低档报名。
- 页面若因整数折扣、平台规则或前端联动而回写活动价：
  - 以页面最终实际显示值为准
  - 记录“批准价 / 页面实际价 / 实际降幅”
  - 页面价低于批准价时标记 `below_target_due_to_platform_forced_discount`，但只要价格精确命中平台档位即可继续提交；页面价与平台档位不一致才阻断
  - 该授权只放行普通营销活动的平台强制档位，不改写人工特殊限时折扣登记价，也不放宽限时折扣利润/底价安全线
  - 活动生效后的订单商品行也按同一平台档位价审计；普通计划批准价继续保留为对照，不得把平台强制价覆盖回普通方案。历史缺失的档位证据登记在 `config/marketing_ordinary_platform_tier_overrides.json`

  - 用户填写 `修改意见/备注` 后，再转换成本期逐行覆盖价文件 `outputs/reports/marketing-price-overrides-YYYY-MM-DD-approved.json`。

  - `--all-open` = 扫描全部未截止可报名活动。
  - 默认排除优惠券活动；只有用户明确要求才使用 `--include-coupon`。
  - 不要把“全部活动”误解成“两天内截止活动”。

- 全选后必须用页面上的 `总计 N 个` 与 `已选商品 N 个` 做一致性检查；不一致时不得进入下一步。
- 大批量活动页即使接口返回完整，虚拟表也可能随机漏挂载少量目标行。整店批量填报出现缺行时，必须改用 `run_ordinary_chunk_submission_batch.mjs` 小块续跑；runner 必须带同一 `--approval-manifest`，`--resume-from` 只能跳过已有干净 execute 证据且 work fingerprint 完全一致的精确 `store + activity + SKC`，不能按店铺或活动整组猜测成功。
- 当前自动化执行入口为 `scripts/marketing/dsy_marketing_deadline_fill.mjs`；该脚本属于营销活动半自动操作入口，不是 Windows 计划任务。
- 脚本默认只完成勾选商品、填写活动价/降幅和复核；只有在用户明确授权“可以提交/自己提交/全自动报完”后，才允许传 `--submit` 点击最终 `提交报名`。首店仍必须先预填不提交，让用户确认页面无误；批量 runner 还必须验证不可变 approval manifest。
- 下一次报新活动前，审核导出入口必须升级或补充为“叠加安全审核”版本：除了现有普通营销活动字段，还必须读取/合并当前和未来可能重叠的普通营销活动、优惠券和限时折扣。若脚本暂时只能导出普通活动，不得把它当作最终可报名审核表。
- 按货号汇总的确认表由 `scripts/marketing/build_marketing_sku_approval.mjs --date YYYY-MM-DD --version vN` 生成；交付前必须跑 `scripts/marketing/verify_marketing_sku_approval.mjs --date YYYY-MM-DD --version vN`。校验至少覆盖：用户标注回归、仓储费缺失不伪装成 0、含仓储利润率不高于不含仓储利润率、利润率与建议最终成交价同口径、券策略明确“仅 15%”或“15/30/50 都禁止”、旧别名不独立出现。仓储证据缺失会告警并要求补证，但不再把不含仓储商品成本口径误判为整份表不可用。

- 重扫漏报或用户质疑漏报时，不要只处理上一次报错活动；必须逐店重新扫描 DSY 店铺（含 `MZ`，除非用户明确排除）在时间窗内仍可报名的活动，发现新增抓入商品就补填。

  - `2026-07-29` 起，对用户已经批准并执行中的普通活动批次，上述差额只要在报名截止前出现，就属于长期授权的自动补报范围：巡检当轮完成 supplement、不可变 approval manifest、dry-run、真实提交和受影响店回读，不再逐次确认。补报优先克隆同店同 SKC 已批准价；没有同店批准行时按当前最终基准和既定 Top5/新品/备注规则计算。平台最低档更低时按平台档提交并审计差额。活动已截止、价格无法可靠推导、身份不一致或平台硬拒绝时才保留 blocker。该授权不包含未批准的新活动方案、永久库存增加和优惠券；已经获得报名授权的普通活动可使用上文“事务式临时补量”，但必须在 `finally` 恢复原可用库存。

  - 大批量真实提交刚完成时，可以做一次全量回读作为最终验收。

  - 普通活动真实提交或回读结束后，不管成功、失败还是用户中途接管提交，都必须调用 `scripts/close_store_browsers.ps1 -Stores <stores>` 关闭本批店铺浏览器；大批量任务结束后再做一次全店关闭和远程调试端口检查，确认没有店铺 profile 残留，避免卡顿、串号和下次误判。

  1. 先填 `提报的活动降幅`
  2. 再填 `提报的活动价格`
  3. 对固定价货号，如页面容易回写，可再次回写活动价确认

  - 所有已选商品都有活动价
  - 所有已选商品都有降幅
  - 无空值
  - 无明显超低价
  - 无平台校验错误

## 七、限时折扣专项规则

限时折扣是商家可随时设置和取消的价格工具，但当前定位不是“只有营销活动空档才用”，而是所有在售运营链接都必须具备的兜底层：它不能替代普通营销活动，也不能在已有普通营销活动上继续压穿目标价。

长期规则（`config/marketing_pricing_policy.json` 也保留同口径机器可读配置）：

- 计划内可报链接原则上必须有一个可解释的限时折扣状态：要么已有不干扰目标价的限时折扣，要么取消/修改旧折扣后重建新的限时折扣；不能因为已报普通营销活动、已有当前售价达标、旧折扣取消过，或优惠券存在，就把该链接跳过。
- 默认限时折扣为 `15%` 折扣（即 `当前售价 × 0.85`），但 `15%` 只是默认起点，不是机械套用。
- 核心校验永远是目标成交价：先按时间窗口取 `min(当前售价, 普通营销活动价..., 限时折扣价...)` 作为不含券保底基准价；优惠券只用于触券下探风险测算，不能用于证明目标价必然达成。若普通营销活动已报并能命中目标，限时折扣仍必须存在，但只能作为不打穿目标价/底价的兜底层；若普通营销活动缺失、未生效或未覆盖，限时折扣必须直接把不含券保底价兜到当前计划目标价。
- 当普通营销活动报名漏掉且报名期已结束时，限时折扣必须作为兜底补救：限时折扣价应直接命中原本计划的目标成交价，不得再依赖 `15%` 优惠券实现目标价；结束时间按该普通活动窗口或一个月默认兜底周期设置，并在下期普通活动恢复后重新校验。
- 如果一个链接已有生效/未来生效限时折扣，先判断它是否干扰本期目标价；会干扰就取消或修改，再按新目标重建。一个链接不能同时依赖多个互相冲突的限时折扣。
- 执行器硬校验：`apply_hl_limited_discount_rescue.mjs` 和 `split_recreate_mixed_limited_discount.mjs` 在写入前硬校验每行必须有 `finalTargetPrice`，且 `limitedDiscountPrice` 不得低于 `finalTargetPrice - 0.01`；缺失或低于目标价的行直接 fail closed，不会机械按 15% 或过深折扣提交。
- 限时折扣漂移修复：`build_limited_discount_drift_rescue_plan.mjs` 从每日 guard 的 `limitedDiscountTargetPriceDrift.belowRows` 构建修复计划，以当前 `finalTargetPrice` 作为限时折扣价。

- 新品/新链接只要进入在售运营范围，无论是否已有普通营销活动，都必须检查限时折扣兜底层；没有普通营销活动或普通活动尚未生效时，限时折扣直接把价格降到目标成交价；已有普通营销活动时，限时折扣默认按 `15%` 或缩浅后的安全折扣存在，但不得低于目标价/底价/利润线。
- 新上架 7 天内且未报普通营销活动的链接，是限时折扣自动处理的高优先级特例：折扣力度按同一标准货号全店全链接 7 天曝光 Top5，活动窗口固定为一周，用于衔接后续普通营销活动；这类链接不等用户再人工确认“是否要兜底”，除非缺成本/目标价/仓储费/底价、库存、店铺身份异常或平台规则阻断。
- 新品/新链接进入价格栈前必须先尝试形成精确 `storeKey + skc` 计划。`standard_goods_sn` 相同不能无脑复制老链接的活动价、限时折扣或优惠券；但若成本、仓储费、底价、货号归并和同一标准货号全局曝光 Top5 数据足够，系统必须直接推导安全 `finalTargetPrice`，写入本轮 rescue / supplement，并执行限时折扣兜底。只有证据不足或规则阻断时才进入“待定价/待确认”。
- 新链接缺 `finalTargetPrice`、`couponFactor`、成本/仓储费/底价或被标为 `excluded` 时，不得生成 `15%` 券报名 dry-run；但若能按上述规则先补出安全兜底价，就不能继续停留在“待定价”。`couponFactor=1` 或备注明确不叠券/禁券时同样禁止补券。
- 已有普通营销活动生效或未来窗口重叠的商品，限时折扣必须作为兜底层存在，但价格不得低于该窗口的目标价/底价/利润线；推荐的 `85折` 只能作为默认起点，不能机械套用。如果 `当前售价 × 85%` 会低于目标价或安全线，必须缩浅折扣比例或直接兜到目标价。
- 已报名优惠券的商品，限时折扣也要测算“触券下探价”；如果 `限时折扣价 × (1 - 优惠券折扣率)` 低于目标价/底价/利润线，优先取消或排除该实验券，不能为了保留券而削弱普通营销活动和限时折扣兜底。
- 新一期活动报名前必须盘点现有和未来限时折扣。若发现旧限时折扣与新营销活动/优惠券重叠后会成为最低价，优先方案是：先在审核表列出风险，用户确认后再取消旧限时折扣或改为更高价格；本阶段不得自动取消。
- 若用户决定重做限时折扣，推荐流程是：
  1. 导出现有限时折扣清单和涉及 SKC。
  2. 按时间窗口计算与普通活动/优惠券叠加后的最低价。
  3. 对高风险旧折扣生成“取消/改价建议表”。
  4. 用户确认后，先取消或调高旧折扣，再按新规则设置新的空档期限时折扣。

## 八、优惠券活动专项边界

优惠券活动与普通营销活动报名不是同一条入口，不得直接复用普通活动页的预填假设。

- 已验证活动 `34810 / 平台优惠券招商活动` 的正确入口是：
  1. 先进优惠券详情页 `#/mbrs/marketing/coupon/detail/34810`
  2. 再点击 `继续报名`，进入 `#/mbrs/marketing/coupon/rule/signup/34810/{levelRuleId}?from=detail`
- 不要使用普通活动 `#/mbrs/marketing/sign-up/config/34810` 路径；该路径会误导为普通活动预装，不能作为优惠券报名成功证据。
- `levelRuleId` 按店铺变化，不能拿 DL 的 `2942` 套全部店。当前活动 `34810` 的 15% 档映射已沉淀到 `config/marketing_coupon_level_rules.json`，用于按钮跳转偶发失败时直达规则页 fallback；该配置不是账号密钥。2026-06-04 已验证 19 店：DL=`2942`、DX=`3003`、FY=`3010`、LQ=`3026`、NM=`3036`、HL=`3017`、JY=`3001`、ZL=`3004`、TS=`1994`、MZ=`2045`、CX=`2000`、YJ=`2034`、XL=`2031`、QY=`2040`、QH=`139`、TZ=`23220`、JSH=`26939`、TZZ=`30104`、XC=`26929`。
- 优惠券批量导入弹窗里的 `确定` 不是“只预填”；它会直接触发真实提报。只有用户明确授权提交时才可点击，否则必须停在导入前/确认前供用户复核。
- `商品提交成功`、`查看报名进度`、`导入成功` 只说明前端已接受导入/提交任务，不是最终报名完成证据。最终证据必须来自 `MULTI_LEVEL_RULE_ENROLLED_GOODS` / `MULTI_LEVEL_ENROLLMENT_RECORD` 的已报/处理中集合回读；若部分店长时间未进入已报集合，必须改用已验证的 direct multi-level `partake` API 或继续回读，不得只按弹窗成功结案。
- 多档券 direct API 已验证入口为 `/mrs-api-prefix/mbrs/activity/multi-level/partake`。payload 必须同时包含 `activity_id`、`partake_rule.partake_rule_id`、`partake_rule.coupon_level_id` 和 `skc_info_list`；只传 `partake_rule_id` 会返回 `4018 参与规则不存在或未生效`，不能作为可重试成功路径。
- 活动 `34810` 在 2026-05-28 执行批次只允许 `15%` 固定券档或不报券；不得生成 `30%/50%` 券，也不得生成小数券折扣。
- 预算恢复走站点预算接口 `/mrs-api-prefix/mbrs/activity/multi-level/modify_site_limit`；所有本期参与店铺的 `shein-sa` 周预算默认按 `1000 SAR` 维护，额度不足或额度用完时先补到 `1000 SAR` 再继续复扫/报名。补预算完成证据只看 execute 后的 before/after 预算回读；`dry-run` 只能做观察/建议，不能替代真实补额度完成。若写入接口返回异常但回读预算已达 `1000 SAR`，按“预算达标但写入异常”记录，不重复盲写。
- 高券研究边界：
  - `30%/50%` 券只允许进入 `scripts/marketing/build_high_coupon_research_candidates.mjs` 生成的 research-only 报告，不允许进入每日 `suggestedDryRunCommands`，也不得调用 `submit_coupon_activity_goods.mjs --discount-max 30/50`。
  - 研究逻辑必须反推 `requiredBasePrice = finalTargetPrice / (1 - couponRate)`，再与活动页平台最低降幅允许的最高活动价比较；若平台最低降幅会把普通活动价压得更低，叠高券后低于目标价，则必须阻断。
  - 缺成本、缺仓储、缺当前售价、缺平台最低降幅、缺 `finalTargetPrice`、旧普通活动/限时折扣会形成更低基准价、或含仓储利润率低于 `15%`，均只能列为“被阻断/需补证据”，不能列为可执行候选。
  - 若高券候选未来要真实执行，必须经过单独审核、用户确认、live dry-run、店铺身份校验、execute、已报集合回读；不得因研究报告存在就自动报名。
- 商品验证优先用 `/mrs-api-prefix/mbrs/activity/multi-level/goods/query?page_num=1&page_size=200`：
  - `page_module='MULTI_LEVEL_RULE_GOODS'`：可报商品集合
  - `page_module='MULTI_LEVEL_RULE_ENROLLED_GOODS'`：已报/处理中商品集合
- 2026-05-28 审计汇总：`tmp/mbrs/coupon-submissions-34810/all-dsy-summary-with-dl.json`，总计 `348` 个唯一 `15%` 券 SKC 已进入已报/处理中集合，批准清单剩余未报为 `0`。
- 后续优惠券不再只按“目标价 - 本次普通活动价”决策；必须先扣除旧普通活动和限时折扣可能形成的最低促销基准价，再决定是否用券。若不用券更接近目标价，应明确标为“不建议用券”。

### 2026-06-14 修正后的长期规则：`allowed15` 只代表可选流量券，不再代表价格保障券

2026-06-04 低价成交复盘曾确认：优惠券执行器不能把 `MULTI_LEVEL_RULE_GOODS` 的“15% 可报集合”或普通活动 selection plan 直接当成应报目标。`可报` 只表示平台允许报名。

2026-06-14 又确认了更关键的事实：优惠券不是每单必然触发，所以 `couponFactor≈0.85` / `普通活动 + 仅15%券` 这类历史口径不能再证明成交价一定达到券后目标。后续 `allowed15` 只能表示“明确批准的可选流量券目标”，不能表示“为了达成目标价必须补的配套券”。

长期规则如下：

1. **目标集合**
   - 15% 优惠券目标不能再直接等同 `ordinary selection-plan`，也不能仅由 `couponFactor≈0.85` 推导。必须先读取 paired `price-overrides`，由共享 classifier 派生 `allowed15`：
     - 只有 combo / note / `couponPurpose` / `couponPolicy` 等字段明确写明“可选流量券、引流、高曝光支持、曝光 Top5、滞销、高库存、清货、试验”等用途，才允许进入 15% 券计划。
     - `couponFactor≈0.85` 但只写“仅15%券 / 普通活动 + 15%券 / 券后目标价”的历史价格保障口径，必须归类为 `price_guarantee_coupon_blocked`，默认不得补券。
     - `couponFactor=1`、combo 含 `不叠券` / `券都禁止` / `15/30/50%券都禁止`，必须排除。
     - `couponFactor` 缺失、combo 空、缺 price-overrides、同一 `store+skc` 多活动口径冲突，一律 fail closed，不自动报名。
   - `MULTI_LEVEL_RULE_GOODS` 中不在 `allowed15` 计划里的 SKC，属于“可报但不应报”，不能自动报名。
   - `MULTI_LEVEL_RULE_ENROLLED_GOODS` 的 active 已报集合最终必须符合 `allowed15` 计划；允许的终态是：
      - 价格保障券 active 数为 `0`；
      - 明确批准的可选流量券 active 数与当前流量券计划一致；
      - `禁止/未知仍 active 数 == 0`
      - `active 但不在 allowed15 流量券计划数 == 0`
2. **提交脚本安全闸**
   - `scripts/marketing/submit_coupon_activity_goods.mjs` 默认必须传 `--target-plan`。
   - 默认执行模式必须是 `coupon-allowed15-intersection-15pct-available`，但这里的 `allowed15` 已是“可选流量券”集合；不能退回 `all-15pct-available`，也不能退回普通活动 plan 全量交集。
   - `--allow-all-15pct-available` 原则上禁用；只有用户单独确认“本次就是独立全量引流券实验”并且预算、底价、触券下探利润均通过，才可作为一次性人工覆盖。
   - `2026-06-05` 起，提交脚本默认会 live 读取当前/未来仍有效的限时折扣活动；目标 SKC 如果仍在 active/future 限时折扣里，限时折扣扫描只能先给出兜底层测算。最终是否低于/命中/高于目标，必须合并同一时间窗口的普通营销活动价、当前售价和限时折扣价，用“不含券的最低促销基准价”对比 `finalTargetPrice`。优惠券只额外计算触券下探风险，不能用来证明目标成交价达标。
   - `--allow-limited-discount-overlap` 只能作为已逐 `SKC` 复核的人工临时覆盖；默认策略仍是价格栈守卫。任何覆盖都要在输出里保留 `effectiveBasePrice/effectiveBaseSource/couponFactor/effectiveFinalWithCoupon/targetFinalPrice/diff`；如果只有限时折扣价证据，必须标记为兜底层候选而不是最终成交价结论。
   - 如果本期计划内 SKC 因旧限时折扣被价格栈守卫排除，默认补救顺序是：先确认不含券保底价是否低于/高于目标价；若低于，取消或修改旧限时折扣；若高于，则用普通活动或新的限时折扣兜底到目标价。不得把补报优惠券作为价格保障补救。
   - 提交脚本还必须加载最新 `marketing-stack-review` 和旧普通活动填报价证据；活动扫描超过 48 小时、stack review 不可用、旧活动价证据目录缺失/解析失败，或目标 SKC 有旧普通/度假季标签但没有旧活动价证据时，写路径 fail closed，不提交。缺证据的下一步是系统只读查价/刷新叠加审核，取不到才报告登录、接口或店铺身份阻塞。提交器遇到登录页或券集合接口 `20302` 时，也要先用真实鼠标点击登录/继续登录并重试，恢复失败才停止为登录阻塞。
3. **只读复扫口径**
   - `scripts/marketing/export_marketing_stack_review.mjs --coupon-target-plan <plan.json>` 会输出 allowed15 配套计划校验列；可额外传 `--coupon-price-overrides <price-overrides.json>` 明确覆盖价来源。遇到 MBRs `20302 子系统登录重定向` 时，脚本会进入登录页并用真实鼠标点击登录/继续登录后重试；仍失败才把具体店铺列为登录阻塞。
   - 叠加审核的 BI 标签上下文默认应使用云端权威快照：`--cloud-bi-ssh shein-bi-tencent --cloud-bi-root /opt/shein-bi/app`，或显式 `--bi-portal-data <data.json>`。输出必须记录 `source.biGeneratedAt / biDataPath / biDataTransport / biFallbackUsed`；不得把本地灾备 `outputs/bi-portal/data.json` 当成实时云端事实。
   - 若用 `rebuild_marketing_stack_review_from_store_audits.mjs` 从已有 store audit 重建，只能刷新 BI context 和汇总表，不能把 `rebuiltAt` 当活动扫描时间；T-3/普通活动候选的新鲜度必须看 `activityScanCreatedAt/activityScanFinishedAt`，并要求 `missingStores=[]`。
   - 优先看 `15%券档active是否符合允许计划`、`15%券档允许配套计划数`、`15%券档禁止/未知仍active数`、`15%券档active但不在允许计划数`。
   - `15%券档剩余未入已报集合数` 是“平台可报但未报”的集合，不等于本期应报目标；如果配套计划已覆盖，这个数大于 0 是正常现象。
4. **取消误报**
   - 多档券已报名商品页是 `#/mbrs/marketing/coupon/rule/goods/{activityId}/{levelRuleId}`。
   - 取消接口是 `/mrs-api-prefix/mbrs/activity/multi-level/partake/cancel`，不是普通活动的 `batch_cancel_partake_goods` / `cancel_activity`。
   - payload 必须来自已报集合里的真实字段：
      - `partake_good_id`
      - `partake_level_rule_id`
      - `partake_rule_good_id`
      - `skc`
   - 取消脚本的“不能误取消”保护集必须是共享 classifier 的 `allowed15`，不是普通活动 selection plan；`allowed15` active 不得被 `riskReason` 绕过。
   - 执行前必须二次加载 coupon classifier plan；任何出现在 `allowed15` 保护集里的 SKC，只有在取消侧重新计算 `最低有效基准价 × couponFactor < targetFinalPrice - 1 SAR` 后才允许作为风险取消目标，否则安全停止。若取消侧只有限时折扣价证据、缺普通营销活动/当前售价证据，必须 fail closed，不得真实取消。
   - 若已确认“旧低价活动 / 限时折扣未结束，叠券会把最终价压低”的风险，必须走显式 `riskCancel` 清单：清单要能加载 paired `price-overrides` 并生成 `allowed15` 保护集、每行保留 `reason/riskReason` 和价格证据，且回读校验只能减少目标风险 SKC，不能误伤其它 `allowed15` 项。不得通过留空 `ordinaryPlanPaths` 或缺失 price-overrides 绕开安全闸。
   - `scripts/marketing/scan_coupon_low_price_overlap_risks.mjs` 是低价叠券只读扫描入口：历史 BI 活动标签只能作为线索，取消候选必须来自 live `34810` active 已报券集合 ∩ live active/future 限时折扣集合。它读到的 `limitedDiscountPrice × couponFactor` 只代表限时折扣兜底层测算；低于目标时可作为 fail-closed 风险线索，高于目标时只能作为“兜底层偏高/需确认普通营销活动覆盖”的候选，不能直接判定最终成交价高于目标。限时折扣列表和商品列表必须完整读取；若登录页、`20302`、限时折扣列表/商品列表查询失败、商品分页截断或券规则 ID 未取到，扫描结果必须标记为不可判定，不能把 active 券数或风险数当作 `0`。
   - `scripts/marketing/scan_coupon_old_ordinary_overlap_risks.mjs` 是旧普通营销活动叠券只读观察入口；旧普通活动重叠本身不得生成可执行取消清单，必须补齐价格栈证据后再进入取消流程。
   - 用户明确授权的“限时折扣 + 优惠券”补救活动必须写入 `config/marketing_allowed_limited_coupon_overlaps.json`，且必须带 `validUntil`；过期后扫描器自动恢复为风险候选。扫描器仍会把这些行写入只读明细，但不会放进自动取消候选，避免把 HL 漏报补救活动误取消。
   - 终止旧限时折扣时，默认只允许结束“整场活动全部是目标 SKC”的限时折扣；如果 live 商品里还有非目标 SKC，必须安全停止，除非用户逐场明确授权 `--allow-mixed-activity-end` 或先拆分/重建活动，避免误伤其它商品价格。
5. **单店试点与回读**
   - 真实取消前先用一个店、一个 SKC 验证接口，确认 `activeExtraRemaining=0` 且 `allowed15` active 数不下降。
   - 批量取消后必须回读 `MULTI_LEVEL_RULE_ENROLLED_GOODS`，不能把“接口 code=0”当作最终成功。
   - 登录页如果是空账号/密码表单，不要反复点 `登录`；应记录店铺登录阻塞，等用户恢复登录后继续。
