# SHEIN 营销活动报名价格规则

## 适用范围

- 适用于 SHEIN 商家后台“营销活动报名”里的活动填报。
- 也适用于报名前的优惠券、限时折扣和既有营销活动叠加风险审核；用户明确要求开始报新活动前，本规则只用于只读审核和生成复核文档。
- 自动化只负责：
  - 勾选商品
  - 填写 `提报的活动价格`
  - 填写 `提报的活动降幅`
  - 滚动复核
- 自动化 **不得点击** 最终 `提交报名`；最终提交必须由用户在可见前端人工审核后点击。
- 页面里 `提报的活动价格（实际生效参考此列）` 优先级最高；`提报的活动降幅` 主要用于配合平台校验。
- 若普通营销活动、优惠券和限时折扣存在时间重叠，报名前必须先做“叠加后最终成交价”审核，不能只看本次活动价。

## 价格叠加安全红线

已验证风险样本：`2026-06-01` HL 店 `SK-04031胶囊咖啡机` 订单净收入 `183.89 SAR`，商品成本 `182.52 SAR`，不含仓储费利润率仅 `0.74%`；同货号 HL 在 `2026-05-31` 的活动标签同时包含 `SA-超级爆品活动-第42期`、`#HLSDdsy1993#限时折扣#2026-05-03#1` 和 `2026年「度假季」常规活动-全托 半托（本地）`。根因模型是：同一时间多个促销价重叠时，SHEIN 取最低促销价；若商品还报名优惠券，则优惠券继续作用在该最低价上。

因此后续所有活动报名必须按以下保守模型审核：

1. 对每个 `店铺 + SKC + 时间窗口`，先列出所有可能生效的价格来源：
   - 当前原始价 / 划线价 / 当前售价
   - 已报名、已生效、未来将生效的普通营销活动价
   - 已设置、已生效、未来将生效的限时折扣价
   - 已报名或计划报名的优惠券活动、券档、预算和生效范围
2. 对每个时间窗口计算最低促销基准价：

   `最低促销基准价 = min(当前售价, 普通营销活动价..., 限时折扣价...)`

3. 若同一时间窗口存在商品可用优惠券，则继续计算：

   `叠加后最终成交价 = 最低促销基准价 × (1 - 商家承担优惠券折扣率)`

   若优惠券状态、券档或预算不确定，按“可能生效的最高商家承担折扣”做高风险测算，不能按无券通过。
4. 利润率必须同时展示两套：

   `商品利润率 = (叠加后最终成交价 - 商品完整成本) / 叠加后最终成交价`

   `含仓储费利润率 = (叠加后最终成交价 - 商品完整成本 - 仓储费摊销/件) / 叠加后最终成交价`

5. 安全判断默认以 `含仓储费利润率` 为主；若仓储费缺失，审核表必须标记 `仓储费缺失/估算缺失`，不得把仓储费按 0 当成已安全。
6. 普通商品默认目标仍按 `30%` 左右利润率；新品/正常品报名前的含仓储费利润率原则上不得低于 `20%`。库存沉淀清货可以按 `15%` 含仓储费利润率作为低价底线，但必须在审核表标红并由用户逐项确认；低于 `15%` 的最终成交价禁止自动报名，除非用户在备注栏单独点名确认。
7. 固定价规则里的固定价从此按“目标最终成交价”理解，不再默认等于“普通活动价”。如果还叠加 `15%` 优惠券，应反推普通活动价；如果已有更低旧活动或限时折扣，则固定价目标视为失效并进入高风险复核。

## 报名前审核文档要求

每次报活动前必须先生成给用户复核的审核文档；用户确认前不得报名新活动、不得批量取消或重报限时折扣。审核文档至少包含以下字段：

| 字段组 | 必填字段 |
| --- | --- |
| 商品定位 | 店铺、分组、活动 ID/名称、SKC、SKU、供方货号、标准货号、商品标题/中文名 |
| 时间窗口 | 报名截止、普通活动开始/结束、优惠券开始/结束或活动期、限时折扣开始/结束、是否与既有活动重叠 |
| 原始价格 | 原价/划线价、当前售价、SHEIN 页面/API 价格字段来源、平台最低降幅 |
| 成本 | 商品完整成本、仓储费摊销/件、含仓储费成本、仓储费口径、成本缺失/仓储费缺失标记 |
| 本次建议 | 建议普通活动价、建议普通活动折扣、建议优惠券券档、建议限时折扣价/折扣、是否建议不用券 |
| 叠加测算 | 最低促销基准价、叠加优惠券后最终成交价、商品利润率、含仓储费利润率、最低价来源 |
| 风险提示 | 旧活动重叠、限时折扣更低、优惠券可叠加、平台最低折扣压价、预算异常、利润率低于红线、缺成本/缺仓储费 |
| 用户复核 | 修改意见/备注、用户确认动作、是否允许低于默认红线、是否需要取消旧限时折扣 |

审核文档应同时提供“明细行”与“按标准货号汇总”两种视图：明细行用于逐 SKC 防漏，汇总视图用于用户快速看价格区间和风险。用户在 `修改意见/备注` 中确认后，才能转换成本期覆盖文件；覆盖文件必须保留用户备注来源。

## 货号归并前置规则

- 报价前必须先做货号归并，统一使用：
  - `config/product_catalog.json`
  - `config/product_aliases.json`
  - `lib/product_sku_normalizer.mjs`
- 仓库侧 `dim.product_match_key()` / `dim.product_canonical_sn()` 必须由 `scripts/generate_product_match_key_schema.mjs` 从 `config/product_aliases.json` 生成并应用，不能手写另一份别名逻辑；否则 ET 仓储明细会按短码散落，确认表会出现缺仓储或旧别名独立行。
- 只有短码、纯数字或 normalizer 标为 `needsReview` 的货号，必须在确认表里标为“货号待归并，暂停”，不得作为可报名 SKU 自动出价。
- 典型归并：
  - `TXSM-505A电动缝纫机` / `SM-505A电动缝纫机` -> 同款
  - `SK-7025绞肉机` / `SK-7025A绞肉机` -> 同款
  - `便携式咖啡机` / `KF-JN-02便携咖啡机` -> 同款
  - `185` -> `SK-185台式榨汁机`
  - `03012` -> `SK-03012台式榨汁机`
  - `03038` / `制冰机` -> `SK-03038制冰机`
  - `SK-3065` -> `SK-GT-3065蒸汽熨烫机`
  - `SK-675` -> `SK-JFB-675B卷发钳和卷发棒`
  - `SK-13065布衣清洗机` -> `SK-13065吸尘器`

## 报价优先级

1. 本期用户确认表 / 备注生成的逐店铺 + 活动 + SKC 覆盖价（row-level override）
2. 用户指定固定价
3. 用户指定利润率
4. 新品保护价
5. 库存沉淀 / 清货候选价
6. 默认利润率规则
7. 平台活动强制档位 / `VIP档` 最低降幅 / 页面回写结果复核（作为最终硬约束记录）

说明：用户在审核表 `修改意见/备注` 中给出的本期要求，只在转换成 `marketing-price-overrides-YYYY-MM-DD-approved.json` 后作为本批次逐行覆盖价执行；除非用户明确要求“同步进长期规则”，不要直接改写上方全局固定价 / 利润率规则。

## 二、用户指定利润率规则

> 这些货号先按指定利润率反推，再对“目标利润率”做小幅随机浮动：
>
> - 下浮 `2` 个百分点
> - 上浮 `1` 个百分点
> - 例如：
>   - `30%` -> 随机落在 `28% ~ 31%`
>   - `25%` -> 随机落在 `23% ~ 26%`
>   - `15%` 清货底线不再下浮到 15% 以下；若平台折扣继续压价，则必须单独复核。

公式：

`活动目标价 = 单台总成本（SAR） / (1 - 实际使用利润率)`

## 三、默认利润率规则

- 除上述固定价 / 指定利润率货号外，其余货号默认按 `30%` 利润率反推。
- 默认利润率也允许小幅随机浮动：`28% ~ 31%`。

## 三点一、新品保护价规则

- 刚到仓不久、且全店/多店上架不足约 `30` 天的新品，不按库存沉淀清货价处理。
- 本轮新增保护：这类新品按各店不同的 `23% ~ 26%` 目标利润率反推活动价，硬底线为 `20%`。
- 若货号同时命中上方“固定价”或“用户指定利润率”规则，必须优先执行用户指定规则；新品保护价 / 清货候选价不得覆盖用户点名规则。
- 若活动页存在 `VIP档`，必须优先满足 `VIP档` 的平台最低降幅；但填报后仍要复核是否明显低于 `20%` 利润率。
- 当前保护价明细输出到 `outputs/reports/marketing-new-arrival-protected-prices-2026-05-12.md`，本期覆盖文件为 `outputs/reports/marketing-price-overrides-2026-05-12.json`。

## 三点二、库存沉淀 / 清货候选规则

- 若商品已有在仓剩余库存，且库存去化周期 `> 6` 个月，按 `15%` 利润率报。
- 若商品已有在仓剩余库存，且库存去化周期 `> 3` 个月且 `<= 6` 个月，按 `23% ~ 27%` 利润率随机报，每个店铺可有差异。
- `15%` 是自动填报硬底线；低于 `15%` 的价格不自动填，除非用户单独点名允许。

## 四、成本来源规则

- 成本来源以当前正式成本链路为准：
  - 正式成本文件：`inputs/costs/成本.xlsx`
  - 营销活动成本映射：`tmp/mbrs/marketing-cost-map.json`
  - 营销活动成本映射生成脚本：`scripts/marketing/build_marketing_cost_map.py`
  - BI 导入脚本：`scripts/import_product_costs.mjs`
- 若货号缺完整成本，自动化不得擅自猜价，必须保留给用户确认。
- 营销活动用的仓储费/件必须来自 BI `profit.productStorageDaily`：
  - 使用当前仍在仓库存的移动平均累计仓储成本。
  - 每日仓储费加入该货号“库存仓储成本余额”。
  - 如果当日仓储数量比上一日减少，减少的数量视为已出库/已不再产生仓储费，并按上一日平均仓储成本从余额中剔除。
  - 新增库存只从入仓后开始承担仓储费，不分摊入仓前的历史仓储费。
  - 禁止用 `profit.products.storage_fee_sar / profit.products.quantity`，因为这里的 `quantity` 是历史销量，会把慢销品仓储费/件夸大几十倍。
  - 若 ET 明细有仓储而确认表显示 `0` 或空，视为系统错误；不得按 0 仓储通过。
- 对于缺“头程运输费金额”的批次：
  - BI 会保留批次记录
  - 但不参与完整单位成本均摊
  - 营销活动成本映射也默认跳过这类不完整批次

## 五、平台折扣与页面回写

- 若平台最低折扣要求更严格，则以平台允许的最高活动价为准。
- 计算方式：

`平台允许最高活动价 = 当前价格 × (1 - 最低折扣要求)`

- 若自动算出的目标价高于平台允许上限，则强制压到平台上限。
- 页面若因整数折扣、平台规则或前端联动而回写活动价：
  - 以页面最终实际显示值为准
  - 但必须记录“脚本目标价 / 页面实际价 / 实际降幅”

## 六、填写与复核要求

- 报名前若用户要求先审核标准，应先导出“按标准货号一行”的审核表，而不是 700+ 行执行明细：
  - 明细采集：`node scripts/marketing/export_dsy_marketing_standards.mjs --stores DL,DX,FY,LQ,NM,HL,JY,ZL,TS,MZ --all-open`
  - 审核交付表：`outputs/reports/marketing-standards-by-sku-YYYY-MM-DD.csv` / `.md`；如需用户直接填写备注，可另存为 `.xlsx`。
  - 用户填写 `修改意见/备注` 后，再转换成本期逐行覆盖价文件 `outputs/reports/marketing-price-overrides-YYYY-MM-DD-approved.json`。
- 活动范围必须按用户口径执行：
  - `--all-open` = 扫描全部未截止可报名活动。
  - 默认排除优惠券活动；只有用户明确要求才使用 `--include-coupon`。
  - 不要把“全部活动”误解成“两天内截止活动”。
- 活动列表必须分页全量读取 `get_activity_list?page_size=100`，不能只读第一页 / 前 30 条；否则会漏掉分页后的活动。
- 进入“选择商品”页后，必须先把右下角每页条数改为 `500 条/页`，再点击全选；不能在默认 `20 条/页` 下直接全选，否则会漏选第 21 个及之后的商品。
- 即使已切到 `500 条/页`，SHEIN 商品表格仍可能使用前端虚拟滚动，DOM 里只挂载可见行；标准导出必须优先使用 `query_supplier_goods_list_v2?page_size=500` 接口全量取商品，并核对接口返回 `total` 与行数一致。
- 全选后必须用页面上的 `总计 N 个` 与 `已选商品 N 个` 做一致性检查；不一致时不得进入下一步。
- 当前自动化执行入口为 `scripts/marketing/dsy_marketing_deadline_fill.mjs`；该脚本属于营销活动半自动操作入口，不是 Windows 计划任务。
- 脚本只允许完成勾选商品、填写活动价/降幅和复核；不得点击最终 `提交报名`，最终提交必须由用户在可见前端人工确认。
- 下一次报新活动前，审核导出入口必须升级或补充为“叠加安全审核”版本：除了现有普通营销活动字段，还必须读取/合并当前和未来可能重叠的普通营销活动、优惠券和限时折扣。若脚本暂时只能导出普通活动，不得把它当作最终可报名审核表。
- 按货号汇总的确认表由 `scripts/marketing/build_marketing_sku_approval.mjs --date YYYY-MM-DD --version vN` 生成；交付前必须跑 `scripts/marketing/verify_marketing_sku_approval.mjs --date YYYY-MM-DD --version vN`。校验至少覆盖：用户标注回归、全表仓储费/件正数、含仓储利润率不高于不含仓储利润率、利润率与建议最终成交价同口径、券策略明确“仅 15%”或“15/30/50 都禁止”、旧别名不独立出现。
- 重扫漏报或用户质疑漏报时，不要只处理上一次报错活动；必须逐店重新扫描 DSY 店铺（含 `MZ`，除非用户明确排除）在时间窗内仍可报名的活动，发现新增抓入商品就补填。
- 若本期已生成价格覆盖表，执行时必须带 `--price-overrides outputs/reports/marketing-price-overrides-YYYY-MM-DD.json`，否则新品保护价、清货底线和本期用户确认价不会全部生效。
- 若本期价格覆盖表包含 `storeKey + activityId + skc`，它必须作为最高优先级逐行覆盖价执行，不能被全局固定价或利润率规则覆盖。
- `SK-13034` 这类用户明确允许“默认最低折扣先填”的缺成本例外，执行时用 `--min-discount-fallback SK-13034`，不得扩展到其它缺成本货号。
- 填报完成后，只保留用户需要人工提交的活动编辑页；关闭活动列表页、中间页和无需提交的店铺窗口，避免前台开一堆页面影响复核。
- 建议填写顺序：
  1. 先填 `提报的活动降幅`
  2. 再填 `提报的活动价格`
  3. 对固定价货号，如页面容易回写，可再次回写活动价确认
- 填完后必须滚动全表复核：
  - 所有已选商品都有活动价
  - 所有已选商品都有降幅
  - 无空值
  - 无明显超低价
  - 无平台校验错误

## 七、限时折扣专项规则

限时折扣是商家可随时设置和取消的价格工具，定位是“填补营销活动空档”，不是在已有营销活动上继续压价。

- 没有普通营销活动生效、也没有即将生效活动覆盖的新品/新链接，可以用限时折扣先把价格降到目标成交价；限时折扣结束时间必须早于下一档普通营销活动生效时间，或在营销活动生效前改为更高的兜底价。
- 已有普通营销活动生效或未来窗口重叠的商品，限时折扣必须高于该窗口的最低普通营销活动价；推荐的 `85折` 只能作为“高于营销价的兜底折扣”，不能机械套用。如果 `当前售价 × 85%` 低于普通营销活动价或导致叠券后低于利润红线，则不得设置 `85折`。
- 已报名优惠券的商品，限时折扣也要按“限时折扣价 × (1 - 优惠券折扣率)”测算最终价；只看限时折扣本身不够。
- 新一期活动报名前必须盘点现有和未来限时折扣。若发现旧限时折扣与新营销活动/优惠券重叠后会成为最低价，优先方案是：先在审核表列出风险，用户确认后再取消旧限时折扣或改为更高价格；本阶段不得自动取消。
- 若用户决定重做限时折扣，推荐流程是：
  1. 导出现有限时折扣清单和涉及 SKC。
  2. 按时间窗口计算与普通活动/优惠券叠加后的最低价。
  3. 对高风险旧折扣生成“取消/改价建议表”。
  4. 用户确认后，先取消或调高旧折扣，再按新规则设置新的空档期限时折扣。

## 八、优惠券活动专项边界

优惠券活动与普通营销活动报名不是同一条入口，不得直接复用普通活动页的预填假设。

- 已验证活动 `34810 / 平台优惠券招商活动` 的正确入口是：
  1. 先进优惠券详情页 `#/mbrs/marketing/coupon/detail/34810`
  2. 再点击 `继续报名`，进入 `#/mbrs/marketing/coupon/rule/signup/34810/{levelRuleId}?from=detail`
- 不要使用普通活动 `#/mbrs/marketing/sign-up/config/34810` 路径；该路径会误导为普通活动预装，不能作为优惠券报名成功证据。
- `levelRuleId` 按店铺变化，不能拿 DL 的 `2942` 套全部店。2026-05-28 执行批次已验证：DL=`2942`、DX=`3003`、FY=`3010`、LQ=`3026`、NM=`3036`、HL=`3017`、JY=`3001`、ZL=`3004`、TS=`1994`、MZ=`2045`。
- 优惠券批量导入弹窗里的 `确定` 不是“只预填”；它会直接触发真实提报。只有用户明确授权提交时才可点击，否则必须停在导入前/确认前供用户复核。
- 活动 `34810` 在 2026-05-28 执行批次只允许 `15%` 固定券档或不报券；不得生成 `30%/50%` 券，也不得生成小数券折扣。
- 预算恢复走站点预算接口 `/mrs-api-prefix/mbrs/activity/multi-level/modify_site_limit`；2026-05-28 DSY 10 店 `shein-sa` 周预算已统一回写并回读为 `1000 SAR`。
- 商品验证优先用 `/mrs-api-prefix/mbrs/activity/multi-level/goods/query?page_num=1&page_size=200`：
  - `page_module='MULTI_LEVEL_RULE_GOODS'`：可报商品集合
  - `page_module='MULTI_LEVEL_RULE_ENROLLED_GOODS'`：已报/处理中商品集合
- 2026-05-28 审计汇总：`tmp/mbrs/coupon-submissions-34810/all-dsy-summary-with-dl.json`，总计 `348` 个唯一 `15%` 券 SKC 已进入已报/处理中集合，批准清单剩余未报为 `0`。
- 后续优惠券不再只按“目标价 - 本次普通活动价”决策；必须先扣除旧普通活动和限时折扣可能形成的最低促销基准价，再决定是否用券。若不用券更接近目标价，应明确标为“不建议用券”。

### 2026-06-03 修正后的长期规则：配套券只跟普通活动计划走

2026-06-03 报名复盘确认：优惠券执行器不能再把 `MULTI_LEVEL_RULE_GOODS` 的“15% 可报集合”直接当成应报目标。`可报` 只表示平台允许报名；本期配套优惠券的真实目标必须是“普通营销活动计划 SKC 与 15% 可报集合的交集”。

长期规则如下：

1. **目标集合**
   - 配套优惠券目标 = `ordinary selection-plan` 中已选 SKC ∩ `MULTI_LEVEL_RULE_GOODS`。
   - `MULTI_LEVEL_RULE_GOODS` 中不在普通活动计划里的 SKC，属于“可报但不应报”，不能自动报名。
   - `MULTI_LEVEL_RULE_ENROLLED_GOODS` 的 active 已报集合最终必须等于普通活动计划集合；允许的终态是：
     - `普通活动计划数 == 15%券档 active 已报数`
     - `已报但不在普通计划数 == 0`
2. **提交脚本安全闸**
   - `scripts/marketing/submit_coupon_activity_goods.mjs` 默认必须传 `--target-plan`。
   - 只有明确审计为“全 15% 可报都要报名”的独立优惠券活动，才允许显式加 `--allow-all-15pct-available`。
   - 配套券的默认执行模式必须是 `plan-intersection-15pct-available`，不能退回 `all-15pct-available`。
3. **只读复扫口径**
   - `scripts/marketing/export_marketing_stack_review.mjs --coupon-target-plan <plan.json>` 会输出普通活动配套计划校验列。
   - 优先看 `15%券档已报是否等于普通计划`、`15%券档普通活动计划数`、`15%券档已报但不在普通计划数`。
   - `15%券档剩余未入已报集合数` 是“平台可报但未报”的集合，不等于本期应报目标；如果配套计划已覆盖，这个数大于 0 是正常现象。
4. **取消误报**
   - 多档券已报名商品页是 `#/mbrs/marketing/coupon/rule/goods/{activityId}/{levelRuleId}`。
   - 取消接口是 `/mrs-api-prefix/mbrs/activity/multi-level/partake/cancel`，不是普通活动的 `batch_cancel_partake_goods` / `cancel_activity`。
   - payload 必须来自已报集合里的真实字段：
     - `partake_good_id`
     - `partake_level_rule_id`
     - `partake_rule_good_id`
     - `skc`
   - 执行前必须二次加载普通活动计划；任何出现在普通活动计划里的 SKC 禁止取消。
5. **单店试点与回读**
   - 真实取消前先用一个店、一个 SKC 验证接口，确认 `activeExtraRemaining=0` 且普通计划 active 数不下降。
   - 批量取消后必须回读 `MULTI_LEVEL_RULE_ENROLLED_GOODS`，不能把“接口 code=0”当作最终成功。
   - 登录页如果是空账号/密码表单，不要反复点 `登录`；应记录店铺登录阻塞，等用户恢复登录后继续。
