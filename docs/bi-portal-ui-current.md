## 2. 首页看板筛选联动

- 首页筛选区必须放在页面最上方统一 sticky 工具栏内，不能放回经营总览卡片或 hero 下方；首页顶部工具栏内有独立筛选区：
  - 货号/SKC/品名筛选：`homeProductFilter`
  - 店铺/分组筛选：`homeStoreFilter`
- 首页顶部筛选栏在桌面宽屏下必须保持单行：货号搜索、店铺/分组、范围提示、清空按钮和时间筛选在同一行内；提示标签要给足宽度，不能互相挤压；在窄屏下才允许按响应式折行。
- 普通子页面筛选栏同样放在顶部 sticky 工具栏，但布局要比首页更克制：全局搜索和货号/SKC/品名框适中，店铺框明显短一些，时间框更长以完整显示起止日期。动作池不显示时间筛选，使用动作池专用筛选。
- 店铺筛选支持：
  - `全部店铺`
  - `DSY 组`
  - `LGM 组`
  - 16 个单店代码
- 首页顶部矩阵、日销趋势、月销趋势、店铺排行、产品排行必须同时受以下条件联动：
  - 时间段
  - 店铺或分组
  - 货号/SKC/品名
- 默认未选择店铺/货号时，顶部矩阵固定显示三行：`总计`、`DSY 组`、`LGM 组`。
- 选择某个分组时，顶部矩阵显示该分组口径。
- 选择某个单店时，顶部矩阵显示该店口径。
- 选择某个货号时，所有指标和趋势按该货号在当前店铺/分组范围内重算。
- 选择“货号 + 店铺”组合时，首页趋势和排行使用 `rankings.dailyStoreProducts` 的店铺×货号日粒度数据，不再只看全局货号汇总。

## 3. 时间筛选规则

- 首页和需要当前时段口径的子页面共用时间筛选逻辑。
- 快捷按钮在时间按钮外侧，常用时间段不用打开弹窗：
  - 今天
  - 昨天
  - 近 3 天
  - 近 7 天
  - 近 15 天
  - 近 30 天
  - 本月
  - 上个月
  - 近 3 个月
  - 近一年
- 点击时间按钮后弹出大号双日历：
  - 左侧选择开始日期。
  - 右侧选择结束日期。
  - 上方同时保留两个日期输入框，方便直接改日期。
- “今天”按电脑当前自然日计算，不用仓库最新销售日冒充今天。

## 3.1 顶部全局筛选与页面局部筛选

- 页面最上方 sticky 工具栏只放真正全局有效的条件：
  - 时间段
  - 店铺 / 分组
  - 货号 / SKC / 品名
  - 全局搜索
- 顶部全局筛选会影响首页、店铺、货号 360、SKC/链接、评价/口碑、订单/售后、成本/利润、实际库存/去化等需要当前时间范围的页面。
- `今日动作池` 是当前最新待办池，不按时间段回看；动作池页不显示时间选择窗口，也不把 `startDate/endDate/rangePreset` 写入当前动作池视图链接。
- `业务域`、`风险`、`处理状态`、`快速聚焦` 只属于 `今日动作池`，必须放在动作池页面顶部 sticky 工具栏里的“动作池专用筛选”区域。
- 动作池专用筛选只影响动作池，不得影响评价、订单/售后、店铺、货号或 SKC/链接页面。
- URL hash 里即使残留 `domain/risk/status/focus`，非动作池页面也必须忽略这些条件，避免出现隐形筛选导致“数据消失”。

## 4. 首页顶部矩阵

顶部矩阵统一为四张卡：

1. 当前时段销售额：范围 × SAR / RMB。
2. 当前时段订单 / 销量 / 动销：范围 × 订单 / 销量 / 动销货号数。
3. 当前时段退货 / 售后：范围 × 数量 / 金额，金额同时显示 SAR 和按 `1 SAR = 1.8 RMB` 估算的 RMB。
4. 当前时段真实利润：范围 × SAR / RMB。真实利润来自成本表和退货保守口径；成本未覆盖时显示“待成本表 / 成本覆盖率”，不得继续用 `25%` 粗估冒充真实利润。

首页、趋势和排行里的成交额默认统一为“净成交额”：买家已发起且未取消的售后申请默认计入退货/反转，包含 `待买家退货`、`待交接`、`待卖家处理`、`待买家选择方案` 等未落定状态；若后续最终取消，再在下一次业务域同步后自动冲回。退货、仅退款、派送失败等反转订单不计入成交额、订单数和销量；利润仍扣这些订单的商品成本；只有真实退货退款额外扣 `13.88 SAR`，仅退款、派件失败、派件异常不重复扣退货派送费。

视觉规则：

- 数字居中。
- 数字字号必须明显大于辅助文字。
- 默认三行顺序固定为：总计、DSY 组、LGM 组。
- 筛选到单店或分组后，不要继续强行展示不相关的三行。

## 5. 趋势图

- 日销趋势和月销趋势上下排列，各占满全宽；图表绘图区要尽量贴近卡片左右边界，避免出现大块空白。
- 趋势图不能通过 `preserveAspectRatio=none` 或类似方式强行横向拉伸；应通过扩大自然 SVG 画布、合理压缩内边距和保留坐标轴可读区域来解决宽度问题。
- 月利润趋势也放在首页趋势区，默认近 6 个月。
- 未选择店铺/货号时，折线包含三条：总计、DSY、LGM。
- 选择店铺、分组、货号或组合后，折线切换为当前筛选范围。
- 日销趋势默认展示最近 30 天。
- 月销趋势默认展示过去 6 个月。
- 当用户选择非单日时间段时，趋势图随选择的起止时间段变化。
- 纵轴使用整数刻度，不显示小数。
- 图上只标关键节点，避免过密。
- 鼠标悬停某个日期/月时，显示完整 SAR 数值，不使用 K/M 缩写。
- 月利润趋势在总计/分组口径下使用扣除分摊仓储费后的利润；筛到单店或货号时显示未扣仓储费的商品经营利润，因为仓储费不能拆到单独货号。

## 6. 排行榜

- 店铺排行默认显示完整 16 店；被筛到分组或货号时，显示当前范围内的完整店铺排行。
- 店铺标签只显示 `DL / DX / HL` 这类店铺代码，不重复写 `DSY / LGM` 前缀。
- 产品排行按标准货号归并，不按店铺后台原始货号拆散。
- `CM-121E美式咖啡机`、`121E美式咖啡机`、`121E`、`CM121E`、`CM-121E` 是同一个 121E 咖啡机标准货号，必须统一归并到 `CM-121E美式咖啡机`；否则 TZ 等店会在货号 360、首页筛选和库存决策里被拆成单独货号。
- 产品排行不显示商品标题，避免标题过长、不同店标题不一致、行高错位。
- 点击店铺排行进入店铺视角。
- 点击产品排行进入货号 360。

## 7. 子页面降噪规则

- 每个子页面顶部要有统一的页面说明卡，说明这个页面回答什么问题、先看哪里、再看哪里、最后怎么下钻。
- 每个子页面说明卡下方要有“本页决策摘要”，用 4 张指标卡先给出当前焦点、风险、动作数量和下一步建议。
- 子页面不要一进来就只堆表格；长明细默认放进复核明细或折叠区。
- 店铺视角重点回答“这个店要先处理什么”。
- 货号 360 回答“这个标准货号该扩、该修还是该淘汰”。
- SKC/链接回答“这条链接该优化、替换、补资料还是不动”。
- 评价/口碑回答“差评、低星和质量投诉集中在哪个货号、店铺、SKC”。
- 订单/售后回答“销售、退货、履约、财务能不能互相印证”。
- 成本/利润回答“真实利润来自哪里，哪些货号值得加码，哪些货号利润差，以及选品前如何估算利润率”。
- 实际库存/去化回答“到仓批次还剩多少、在途能否接上、哪些货号快断货或库存沉淀”。库存基数来自成本表批次，销售扣减使用毛销量保守口径。
- 今日动作池回答“今天先处理什么”，口径是当前最新待办池，不随时间筛选回看历史。
- 今日动作池同一店铺、同一 SKC、同一业务域的多条规则命中要合并为一张动作卡，显示“合并 N 条”和每条规则信号，避免同一链接重复处理；跨业务域动作仍保留独立卡片。
- 订单/售后和今日动作池如果被筛选为空，但底库仍有数据，必须显示可读提示；订单/售后只提示顶部全局筛选或时间段，动作池则同时提示本页专用筛选。
- 系统状态回答“今天的数据能不能放心看”。
- 系统状态允许区分“历史自动任务失败但已恢复”和“当前数据不可用”：`2026-05-09 04:20` ET 同源探测问题已修复并复验，`2026-05-09 05:30` / `07:00` 已正式自动跑通后，不应继续把早期 Docker/WSL 或 ET 登录恢复态显示为当前待验证。

## 8. 店铺视角当前规则

- 选中单店后，不再显示全局“销售最高店 / 风险最高店”，避免误认为本店结论。
- 店铺页时间筛选放在顶部筛选区，当前时段销售、订单、销量、动销、售后申请数都跟随时间段变化。
- `风险分` 是店铺综合优先级分，用来排序“先看哪个店”，不是销售额或金额。
- `动作分` 是单条动作的优先级分，用来排序“先处理哪条动作”，不是金额或销量。
- `在途单 / 在途收入` 来自财务收入明细最新快照，主要用于回款和对账复核。
- 同货号重复链接对比必须展示同组全部 SKC，并给出当前最佳、弱于最佳、淘汰候选、可果断下架、先推替代等清晰判断。
- 链接指标统一按 `曝光 -> 访客 -> 销量 -> 支付率` 展示，并在每个指标下显示 `7 天 / 30 天` 二级表头。
- 本店低展示库存预警来自 `fact.visible_inventory_snapshot` 最新正确展示库存快照，不使用备货信息里的虚假库存。

## 9. 评价 / 口碑当前规则

- 评价底库按每店开店以来全量补抓。
- 日常新增评价同步默认只抓最近 `14` 天作为防漏增量窗口。
- 评论中文翻译使用 SHEIN 评论列表接口的 `translate: 1` 平台译文，写入 `fact.product_comment.goods_comment_content_zh`。
- 页面保留原文和中文译文，不依赖浏览器插件实时翻译。
- 当前全量结果：16 店共 `1796` 条评价，`1794` 条有 SHEIN 平台译文；剩余 2 条为原文为空。
- 当当前时间段没有评价但底库有历史评价时，页面必须明确提示“不是底库丢失，是时间段或筛选条件为空”，并引导切换近30天/近一年或清空筛选。

## 10. 成本 / 利润当前规则

- 成本/利润页独立为一个子页面，不塞进订单/售后页。
- 首页“真实利润”和成本/利润页都随顶部时间、店铺/分组、货号/SKC 筛选联动。

- 成本/利润页下方的月度利润明细、高利润/低利润货号、成本覆盖缺口，也必须跟随同一套筛选；只有“历史样本：体积 × 利润率”可使用成本表全量样本，并在页面文案中明确这是选品样本而不是当前销售利润表。
- 高利润 / 低利润货号分界线固定为 `20%` 利润率：`>= 20%` 为高利润 / 可加码，`< 20%` 为低利润 / 需要处理。
- 商品/店铺/货号层利润口径：`净营收 - 商品成本 - 退货派送费`。
- 买家已发起且未取消的售后申请、退货、派送失败等需要保守处理的订单：营收按 `0`，仍扣商品成本；只有真实退货退款链路额外扣 `13.88 SAR` 退货派送费。
- 同货号分批发货时，单位成本按“完整批次总成本 / 完整批次发货总数”计算。
- 发货批次缺“头程运输费金额”时，只保留为缺口，不纳入单位成本均摊，避免成本被低估。
- 月仓储费是所有货一起的月总数，只用于月度总利润；DSY / LGM 按当月成交额比例分摊，不拆到单独货号。
- `TS`、`MZ` 在 `2026-03-01` 前归 `LGM`，从 `2026-03-01` 起归 `DSY`。
- 成本覆盖不足时页面必须显示覆盖率和缺成本销售额，不允许用预测利润填补空白。

## 10.1 实际库存 / 去化页面口径

- 实际库存/去化页独立为一个子页面，不塞进成本/利润或订单/售后页。
- 页面顶部回答三件事：估算在库、在途/待确认、加权日销和高风险货号数量。
- 到仓库存来自成本表批次：`到仓/派送日期` 和 `头程运输费` 都有值才计入已到仓；有发货日期但缺其中任一项计入在途/待确认；没有发货日期计入未发/待确认。
- 库存消耗用毛销量扣减，不用净成交销量；退货暂不加回库存，避免高估可售库存。
- 店铺/分组筛选只影响销售速度和风险排序，不硬拆物理库存；成本表没有店铺分配数据前，库存基数保持全局货号口径。
- 页面必须明确提示“这是估算库存，不是仓库系统实盘”；未来接入真实仓储系统后再升级到货号 × 店铺/仓库粒度。

- 选品计算器用于模拟售价、采购价、头程、其它成本、退货率和体积对利润率的影响；体积只做选品参考，不直接扣单品仓储费。

- 选品模块当前升级为“选品标尺模型”：用真实历史利润校准 `进货价 × 倒推体积` 矩阵，再提供新选品保本售价和 25% 利润率售价试算。当前成本表没有物理长宽高，体积由历史头程按约 `1600 RMB/方` 倒推；新选品未来头程按 `2000 RMB/方` 重算。

## 11. 主题和美观

- 支持浅色 / 深色主题切换。
- 浅色主题不能出现灰底灰字。
- 数字列统一使用 tabular nums。
- 排行、矩阵、二级表头、证据网格必须对齐，不能用 `<br>` 或小卡片硬拼造成错位。

## 11.1 V2.1 独立经营 BI 预览原则

- V2.1 当前目标是独立经营 BI 预览版：不复制 V1 DOM，不做简单换肤；只读取 `outputs/bi-portal/data.json`。
- 视觉方向：暖白底、炭黑字、低饱和状态色、紧凑页头、低噪声背景、收敛圆角和阴影。
- V2.1 首页当前验收标准是“功能和操作逻辑完整复刻 V1 首页，视觉重新设计”：顶部货号/品名/SKC 搜索、店铺/分组、时间筛选、四个经营矩阵、净/总销售额切换、净/总销量切换、退货时间口径切换、利润口径切换、日/月趋势、趋势指标切换、店铺/货号排行下钻、深浅主题都必须可用。
- V2.1 首屏优先展示“今日经营总览 + 动作优先级 + 核心指标 + 趋势”，避免营销落地页式大空白。

## 12. 门户修改验证规则

- 侧栏每个数据域只显示一条精确到秒的更新时间；数据口径日放在鼠标悬停提示里，避免同一数据域显示两个时间。
- `链接表现数据` 的更新时间必须显示 SHEIN 链接源文件抓取时间，即 `outputs/shein_links/<店铺>/<链接日>.json` 内的 `fetchTime` 最大值；`售后/库存/财务数据` 的更新时间必须显示业务域源文件抓取时间，即 `outputs/shein_business_domains/<店铺>/<业务日>.json` 内的 `fetchTime` 最大值；不要显示 BI 重跑时重新入仓的 `updated_at`，否则会误导成“又重新抓了一次后台数据”。

- 修 BI 门户 UI 时，默认不主动打开前端；用户会在自己的浏览器刷新查看。
- 默认验证方式：
  - `node --check scripts/generate_bi_portal.mjs`
  - `node scripts/generate_bi_portal.mjs`
  - `node scripts/check_bi_portal_ui.mjs --json`
  - 静态检查 `outputs/bi-portal/index.html`
  - 静态检查 `outputs/bi-portal/data.json`
- 只有用户明确要求，或必须排查浏览器交互、滚动、弹窗、控制台错误等问题时，才打开前端页面验证。
- 如果问题本身是页面布局、宽屏留白、对齐、卡片挤压、图表绘图区等视觉判断，且用户要求打开前端，应使用最大化 / 大视口验证；不要用未最大化小窗口或只看代码来判断宽屏效果。


## 13. 成本 / 利润页细化

- 利润页当前结构固定为：先看结论 → 月利润趋势 → 高利润/低利润货号 → 选品标尺/利润试算 → 成本覆盖缺口。
- 顶部“先看结论”必须直接告诉用户当前筛选范围是否赚钱，并显示净成交、商品成本、反转订单和仓储口径。
- 货号表必须给出“建议动作”，例如可加码、控退货、调价/淘汰、先补成本，不能只堆财务数字。
- 选品模型放在后段作为决策工具，不抢占利润经营结论的阅读优先级。


## 14. 订单 / 售后复核台

- 订单 / 售后页不是订单流水页，而是经营复核台，核心回答三件事：成交是否真实、售后压力来自哪里、哪些订单/货号需要复核。
- 页面主区先显示“这页先看什么”、订单销售、售后金额、财务待结算、履约异常/取消和优先复核对象。
- 财务店铺摘要、营销活动、在途订单、商品/SKC、订单明细、售后明细、履约明细都放到下方折叠证据区，需要查单时再展开。
- 优先复核对象按售后金额聚合到货号和店铺，点击可带筛选跳转，避免用户一进页面就面对多张长表。
- 订单明细必须按订单创建时间跟随顶部时间段；售后明细必须按售后申请时间跟随顶部时间段；履约明细按揽收/打印/快照时间跟随顶部时间段；财务订单/SKC 明细按财务订单发货日跟随顶部时间段。
- 财务店铺摘要是最新财务快照，只用于看待结算、在途和账期，不冒充历史月份数据；如果和当前筛选时间段不同，页面文案必须明确标注“最新快照”。
